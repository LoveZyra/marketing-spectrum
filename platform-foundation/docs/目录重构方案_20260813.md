## 一、现状体检

`ma_server/` 现在是四个平级目录，里面混着三类生命周期完全不同的东西，而线上它们分散在**三个互不相干的根**下。

| 本地 | 实际是什么 | 线上住哪儿 |
|---|---|---|
| `marketing-audit/` | skill 源码 | `~/.claude/skills/marketing-audit/` |
| `hdfs-data/` | skill 源码 | `~/.claude/skills/hdfs-data/` |
| `schedule_task/` | skill 源码（定时任务**框架**） | `~/.claude/skills/schedule-task/` |
| `营销诊断/ma-api-mode/` | 常驻 HTTP 服务 | `~/prism/ma-api-mode/`（`restart_prism.sh` 还要放 `~/prism/`） |
| `营销诊断/私域平台诊断/` | 固定流程 driver（按活动手工触发） | `/home/jovyan/营销诊断/` |

### 六个具体问题

**1. 目录名不等于线上路径，同步全靠人记。**
这次部署 fix29 时，我是靠翻 8 月 3 日的处置方案才确认「skill 走 `install_skill.sh`、API 走 `~/prism/ma-api-mode/install.sh`、重启走 `~/prism/restart_prism.sh`」。这条信息不在仓库里的任何地方。

**2. 目录名和 skill 名对不上。**
本地叫 `schedule_task`（下划线），skill 名是 `schedule-task`（连字符）。skill 目录名必须与 `SKILL.md` 里的 `name` 逐字一致，拷错就是不被识别。

**3. 更糟的是这个名字在线上还指着另一样东西。**
`~/.claude/skills/schedule-task/` 是**框架**，而 `/home/jovyan/schedule_task/` 是**任务实例根目录**（`<任务名>/{logs,tasks,work}`）。本地那个 `schedule_task/` 装的是前者、名字像后者。

**4. 本地和线上都不是全集。**
你刚给的 bundle 里有 `html-edit-mode` / `onesql` / `upload-html` —— 本地一个源都没有；而 `marketing-audit` 又不在 bundle 里。**改哪个都不留痕。**

**5. 没有 git，发布产物和源码同居。**
`ma-api-mode/` 下躺着 `ma-fix12` ~ `ma-fix19` 八个 tar.gz（约 1.4MB）；`marketing-audit/` 根目录一个 fix29 包、`dist/` 一个 fix26、`dist/_to_delete/` 里还有一个 10MB 的。版本历史全靠 tar 包名，回滚只能靠解包比对。

**6. 定时框架与被定时跑的东西之间没有任何指向。**
线上 crontab 现在有一条：

```
0 0 * * 1  /home/jovyan/schedule_task/weekly_356352_356353/tasks/run.sh
```

这个任务的 `tasks/prompt.md`（提示词本身就是逻辑）**只存在于服务器上**，本地无源、改了无痕。

### 一个新文件该放哪 —— 三条判定规则

按顺序问，第一个「是」就落位：

1. **它会被 `~/.claude/skills/` 装载吗？** → `skills/<name>/`。目录名必须等于 `SKILL.md` 的 `name`。
2. **它是一个一直开着的进程，改完要重启吗？** → `services/<name>/`。
3. **它跑一遍就结束（不管是 cron 拉起还是手工敲）吗？** → `jobs/<name>/`。

都不是 → `docs/`。

`jobs/` 里再用 `JOB.md` 的第一行区分触发方式（`trigger: cron` / `manual` / `api`），**不为此再开一层目录** —— 触发方式会变，部署位置不会。

## 四、迁移步骤

**前提：先 `git init`。** 现在没有版本控制，重构本身就是一次不可回滚的大规模改名 —— 先把现状存下来，每一步都能退回去。

| 步 | 动作 | 风险 | 可否回滚 |
|---|---|---|---|
| 0 | `git init` + `.gitignore`（`__pycache__/`、`*.pyc`、`dist/`、`runs/`、`logs/`、`feedback/*.jsonl`、`_to_delete/`）→ 首次提交存档现状 | 无 | —— |
| 1 | 清垃圾：删 `__pycache__/`、`_to_delete/`（含那个 10MB 的）、`.probe` 文件 | 无 | git |
| 2 | 建 `skills/` `services/` `jobs/` `dist/` `docs/`，`git mv` 现有四个目录就位；`schedule_task` → `skills/schedule-task` | 低。**纯改名，不改内容** | git |
| 3 | 发布包全部归到 `dist/<组件>/`，只保留最近 2～3 个版本，其余删（线上已有的版本，包在不在本地都不影响回滚——线上是 `.bak_<时间戳>` 机制） | 低 | git |
| 4 | 4 份复盘 md + 运行说明 + 接口说明 → `docs/` | 低 | git |
| 5 | ~~取回缺的三个 skill 源~~ **08-13 已完成**：`html-edit-mode` / `onesql` / `upload-html` 已落本地，`schedule-task` 已换成线上新版并改名（旧版在 `_to_delete/`）。运行时快照（`runtime_env.sh` / `bigdata_env.sh` / `claude_bin.env` / `crontab.txt`）按约定不进仓库 | 低。只读取回，线上未动 | —— |
| 6 | 写 `README.md` 映射表 + 各 `DEPLOY.md` / `JOB.md` | 无 | git |

**全程线上零改动。** 本地目录怎么摆，跟线上路径无关 —— 线上路径写在映射表里，装的时候照表拷。

## 五、三个待确认项（2026-08-13 已定）

| 问题 | 结论 | 对方案的影响 |
|---|---|---|
| `私域平台诊断/` 线上住哪儿 | **`/home/jovyan/营销诊断/`** | 映射表的洞补上了；三个 driver 直接覆盖，`runs/` 是运行产物不碰 |
| cron 任务 `weekly_356352_356353` 要不要纳管 | **不纳管** | `jobs/` 只放固定流程 driver；cron 任务实例（含 `tasks/prompt.md`）继续只存在于服务器上 |
| `ma_api_b.py` 还用不用 | **还在用** | `services/ma-api/` 不瘦身，`DEPLOY.md` 必须写清 B/C 两条路与各自 runner |

**cron 那条要留意的**：`~/schedule_task/<任务名>/tasks/prompt.md` 是「提示词即逻辑」，不纳管意味着它改了不会有任何痕迹，pod 重建也只能靠 `_shared/crontab.txt` 那份备份恢复 crontab 条目、恢复不了 prompt。这是明知的取舍，不是遗漏。

**任务本身照跑**（2026-08-13 确认）：`weekly_356352_356353` 的 crontab 条目保持不动，只是仓库不跟踪它。线上现状随时可用 `_shared/list_tasks.sh` 查。

## 六、明确不做的事

- **不按业务域切。** 「营销诊断」这条线会被拆进 `skills/` `services/` `jobs/` 三处——这是有意的：同类东西的装法、重启方式、谁能改，必须一处说清，否则映射表会长成三倍。业务归属靠 README 里的一句索引解决，不靠目录。
- **不为 cron / 手工触发再开一层目录。** 触发方式会变，部署位置不会。
- **不动线上目录结构。** 线上 `~/.claude/skills/` 和 `~/prism/` 的布局由 Claude Code 和 Prism 决定，不是我们能重排的。本地仓库的职责是「有源、有痕、有映射表」，不是镜像线上。
- **不把运行时数据纳入仓库。** 日志、`runs/`、`feedback/*.jsonl` 一律 gitignore —— 尤其 `feedback/`，它是跨版本持久账本，进了包就会覆盖线上。
