# 10 — 用户反馈处理协议 (贯穿全流程)

> 本文规定 Agent 遇到用户反馈时的处理方式。**沉淀机制只有"人工晋升"这一条链路**：
> Agent **不读取**任何历史账本（决议见《自迭代沉淀机制·可行性评估》§三），
> 只负责把反馈**准确地记下来**。记错一条的代价远大于漏记一条。

---

## 0. 前置：账本是什么、不是什么

`feedback/issues.jsonl` 沉淀的是**跨活动反复出现的问题**，供创建者定期 `cli issues report` 评审后
人工改规则。它**不影响本次诊断的任何判定**，也**永远不会自动修改 `diagnostic_rules.yaml`**。

---

## 1. 先分流：三类反馈走三条路，只有一类进账本

用户说"这里不对"时，**先判断是哪一类再动作**：

| 类型 | 典型说法 | 处理 | 进账本？ |
|---|---|---|---|
| **① 本次报告写错了** | 数字引错、人群断链、措辞不符事实、建议与 finding 对不上 | **当场改这次的报告**，走 `self_critique` 的既有归宿（修订/接受为 caveat/复诊/移入 blind_spots/删除） | ❌ 不进。同类问题反复出现时，`validator_warn` 的自动采集自会冒出来 |
| **② 规则 / 口径有问题** | 条件不对、阈值不合理、适用范围错、建议业务上不可执行 | 进账本；**不改本次判定**，可在 `data_caveats` 注明「业务侧对该口径有异议」 | ✅ **唯一需要记账的一类** |
| **③ 数据有问题** | 字段缺失、口径与数仓不符、值域异常 | 进账本（`kind=data_mismatch`）+ 进本次 `data_caveats` | ✅ |

> 把三类都倒进账本的后果是：80% 是一次性的报告瑕疵，创建者翻两次就再也不看了。

---

## 2. 先核对，必要时反驳，而不是先记录

你手上有本次的 `rule_summary`（含 `recommendations` / `applies_to` / `condition` / `skip_reason`）
和 `diagnostic_rules.yaml` 的 `description`，**足以判断用户的反馈是否基于误解**。
2026-08-12 规则改版后，以下三种误解尤其常见：

| 误解 | 核对方式 |
|---|---|
| 把 #43 的结论当成 #11 的 | 两条现在几乎同一批人（43 = 11 ∧ `pre_mainflow_event_cnt>0`），确认用户说的是哪条 |
| 对**已下线**规则提意见（#15/16/17/18/24/40） | 它们 `enabled: false`，根本不产出 finding，报告里那句话不可能来自它们 |
| 把「规则没触发」当成「规则有问题」 | 可能是 `min_trigger_rate`（#41 的 5%）或 `scope_filter`（#45 仅广告投放）**按设计**拦下的 |

- **核对后不成立** → 先向用户解释，不要急着记。用户接受解释就不记。
- **核对后不成立但用户坚持** → **仍然要记**，带 `--verdict disputed` 和你的核对依据。
  这种分歧往往说明**报告措辞或文档有问题**，本身就是一个真实待办。
- **核对不了**（缺数据、超出本次范围）→ `--verdict unverifiable`。

---

## 3. 写之前必须复述确认

把反馈整理成结构化条目**念给用户听，得到确认后才调用 `cli feedback`**：

> 我把它记成这样：
> **规则** #11 跨品类推送错配 ｜ **问题类型** 适用范围不对（`wrong_scope`）
> **范围** 系统性（影响后续所有活动）
> **具体**：目标品类零接触的判定对新客不成立，新客本来就什么都没浏览过
> **我的核对**：确认成立 —— #11 当前没有排除新客，`type_mem` 字段在 registry 里有但规则没用到
> 这样记对吗？

- 用户纠正 → 改完再写。
- 用户没回应 / 话题已经过去 → **不写**。
- 用户只是情绪化表达（"这报告没用"）而给不出具体指向 → **不写条目**，追问一句到底哪里没用。

写入命令：

```bash
python3 cli.py feedback --source user --kind wrong_scope --scope systematic \
  --rule 11 --campaign 1000344 --reporter 张三 \
  --verdict agreed --note "核对依据：#11 未使用 type_mem 字段" \
  --quote "新客本来就没浏览过，这条对新客不成立"
```

> `--quote` **必须是用户原话**。你的转述放 `--note`，两者并存 ——
> 创建者需要看到原话来判断你的转述有没有偏。

`--kind` 是封闭枚举：`wrong_scope`（适用范围）/ `rule_semantics`（条件阈值口径）/
`advice_infeasible`（建议不可执行）/ `data_mismatch`（数据口径）。**不要自造。**

`--scope` 决定创建者要不要改规则：`this_job`（这次数据特殊）/ `systematic`（规则本身的问题）/
`unknown`（判断不了）。**判断不了就写 unknown，不要猜。**

---

## 4. 隔天反馈：怎么对上号

报告**不带** `rule_id` / `job_id` 标识（决议：不污染运营阅读体验）。用户隔天来提意见时：

1. 让用户报**活动 ID**（报告开头就有，他们一定知道）；
2. 到该活动的 job 输出目录读 `diagnosis_report.json` —— finding 与 `rule_id` 的对应关系在里面是齐的，
   只是没渲染到 HTML 上；
3. 按用户的自然语言描述（"关于弹屏那条""第三个问题"）在 findings 里匹配；
4. **必须走第 3 节的复述确认对号** —— 没有标识之后，这是唯一的对号防线；
5. **匹配不上也不许丢反馈**：省略 `--rule`、`--scope unknown`，但 `--quote` 原话照记。
   宁可让创建者多花两分钟人工判断，也不能因为对不上号就把用户的话吞掉。

---

## 5. 矛盾反馈：不裁决

同一条规则收到相反方向的反馈（甲说太松、乙说太紧）——**照常各记各的**。
账本折叠时会自动标 `conflicting`，两条原话都保留，评审报告里单列一节。
**规则的松紧是业务判断，不由 Agent 替人决定。**

---

## 6. 本次报告要不要跟着改

**默认不改**（否则同一份数据因为聊天内容不同而产出不同报告，破坏"同数据同结论"）。

唯一例外：用户明确说"**这条 finding 不成立**"。这属于 `self_critique` 的 questioned 项，
按 `SKILL.md` 硬门槛的既有要求给它一个显式归宿即可（修订 / 接受为 caveat / 复诊 /
移入 blind_spots / 删除），**走现成路径，不需要新机制**，且会记进 `_decision_trace`，可复现可回溯。

---

## 7. 闭环由人传递，不由 Agent 播报

用户提了意见要知道后来怎么了，否则第二次就不提了。但**Agent 不读账本**，
所以不会在下次诊断时自动播报"你上次提的问题已修"。
闭环方式：创建者在 `cli issues report` 里看到 `status` 变更后，当面/在群里告知提出人；
`--out` 的评审报告里带有 `reporters` 字段，便于转发。
