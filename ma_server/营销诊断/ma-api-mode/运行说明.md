## 1. 这个目录里都有什么

**服务代码四个**，是主体：`ma_core.py` 是 HTTP 服务骨架（路由、鉴权、任务存储、并发闸门、调 claude 的封装），`ma_pipeline.py` 是全部业务逻辑（取数、诊断、圈人、出 SQL、发布报告、口径收口），`ma_api_c.py` 和 `ma_api_b.py` 分别是方案 C 和方案 B 的入口——两个方案共用前两个文件，差别只在编排方式。

**回归套件五个**：`regress_direction.py`（圈人口径）、`regress_polish.py`（润色链路接得住）、`regress_critique.py`（门禁分得清 schema / lint / 渠道）、`regress_agent.py`（报告产出 Agent）、`regress_env.py`（环境体检 / HTTP 长连接不串包 / Prism 自启的拒绝阶梯）。五套加起来 532 条断言，改完代码跑一遍，全过才算数。这些不是摆设——fix6 就是靠 `regress_critique` 抓出来三条断言还停在旧口径上。

`regress_env.py` 钉的这三块有个共同点：**出事的时候不报错**。体检本身写错了没人会发现，它平时就该一句话不说；长连接串包只在同一条 keep-alive 连接上连发多个请求时才犯，`curl` 每次新开连接根本测不出来（所以那一节是裸 socket 手写的请求）；自启的判断是照着 Prism 侧 `ma-service.js` 抄的一份 Python 镜像，两边只要有一边改了，就会变成"体检说没问题、Prism 说不挂载"。这类东西只能靠回归钉。

**环境体检**：`preflight_ma_server.py`。不起服务，只看这台机器配得对不对——报告链接的前缀会不会指到测试机或本机、发布目录在不在、取数脚本和 skill 在不在、端口有没有被占、Prism 的反代和自启会不会被拒。`python3 preflight_ma_server.py` 直接跑，`--no-network` 跳过所有探测。同一套体检在服务启动时也会自动跑一遍，致命项直接拦住不让起。

**跑批脚本三个**：`run_real_c.sh`、`run_real_b.sh` 是下午那台测试机上用的；`run_ma_server.sh` 是 ma_server 上用的（`bash run_ma_server.sh c` / `b`）。都不是玩具，是实际把服务拉起来、下单、轮询、打印出参、核对发布物的完整一轮。

**安装脚本**：`install.sh`，配合 `ma-fix7.tar.gz` 用，见第 2 节。它自己会备份、覆盖、语法自检、跑完五套回归，任何一步不过就停下来，不会把一个半装的状态留给你。

**结论与证据**：`方案B与方案C对比结论.md` 是给人看的结论（**注意看它开头的更正声明**），`运行证据/` 是支撑那份结论的原始文件，`截图/` 是两份报告的实际渲染效果。

`运行证据/jobs/job_20260728_234954_2f1521/run/crowd_rules.json` 这个文件**别删**。`regress_direction.py` 的 `find_real_rules()` 会去 glob 它，拿真实的 skill 产出做一遍回放。删了那套回归会从 30 条断言悄悄掉到 25 条——不报错，只是少测五条，比报错更难发现。

## 2. 部署与升级

测试机 `43.167.214.72`，工作目录 `/home/ubuntu/demo/ma-api-mode`，人群池 CSV 在 `/home/ubuntu/特价机票-正式.csv`（GB 系编码，脚本里写死 `gb18030` 读）。两个 skill（`marketing-audit`、`hdfs-data`）已装在 `~/.claude/skills/` 下，**不要重装、不要改**。公司 ma_server 上的路径和这些完全不同，见第 9 节。

## 3. 环境变量契约

所有变量都在**模块导入时**读取并算成模块级常量。必须在 `python3 ma_api_x.py` 之前 `export`，进程起来之后再改没有任何效果。这条踩过一次，记住。

**服务层**（`ma_core.py`）：`MA_API_HOST` 默认 `127.0.0.1`，`MA_API_PORT` 默认 `8091`，`MA_API_KEY` 不设就是不鉴权，`MA_CLAUDE_BIN` 默认 `claude`，`MA_CLAUDE_TIMEOUT` 默认 120 秒，`MA_JOBS_DIR` 默认 `./jobs`，`MA_MAX_CONCURRENCY` 默认 2（方案 B 在没显式设置时会强制改成 1）。请求头是 `x-ma-api-key`，请求体上限 64 KB。**2026-07-30 契约收窄新增一个**：`MA_PUSH_SOURCE`（model/rule/both，默认 both，原入参 `push_source` 挪过来的，配错会在启动日志吵一声并按 both 跑）。原入参 `pull_partition` 直接取消，没有对应的环境变量——特征表是**一张固定表、无分区**（2026-08-03 落定 `app_dm.tmp_ctj_marketing_audit_features_hebo`；**fix14 改为 `app_dm.tmp_ctj_marketing_audit_sample_hebo`，与人群池同表**），取数只按活动 ID 过滤：`--where activity_id='<activity_id>'`。过滤列名由 `MA_FILTER_COL` 控制（默认 `activity_id`，老表是 `task_id`）——**列名配错不报错，只会捞回 0 行然后产出一份"什么都没发现"的空报告**，换表必查这一项。人群池表（圈人计数与 push_sql 的 FROM）同日落定为 `app_dm.long_ctj_marketing_audit_sample`，**但该表一直未建成（1000344 单降级路径查它直接崩）；fix14（2026-08-03）起特征表与人群池统一为 `app_dm.tmp_ctj_marketing_audit_sample_hebo`，换表用 `MA_FEAT_TABLE`/`MA_POP_TABLE`，换表必查 `MA_FILTER_COL`**。再强调一遍方向：整条链路对这两张表**只读不写**，圈人计数也全是 SELECT。

**数据源**：`MA_CSV`（**注意不是 `MA_CSV_PATH`**，默认 `/home/ubuntu/特价机票-正式.csv`）、`MA_CSV_ENCODING`、`MA_CSV_MAX_ROWS` 默认 50 万行、`MA_ID_COL` 默认 `mapid`、`MA_UNION_COL` 默认 `unionid`、`MA_FEAT_TABLE` 默认 `app_dm.tmp_ctj_marketing_audit_sample_hebo`、`MA_FILTER_COL` 默认 `activity_id`、`MA_POP_TABLE` 默认 `app_dm.tmp_ctj_marketing_audit_sample_hebo`（**fix14：特征表与人群池统一为这张 sample 表**，fix10 落定的 `app_dm.long_ctj_marketing_audit_sample` 未建成即弃用；新表的活动 ID 过滤列若不叫 `activity_id` 必须配 `MA_FILTER_COL`，主键列若不叫 `mapid`/`unionid`，用 `MA_ID_COL`/`MA_UNION_COL` 调）。`MA_POP_FILTER` 默认 `auto`（fix15）：两表同名时，人群池侧查询（quantile/count_rules/count_push_total）与出参 `push_sql` 自动前置 `{MA_FILTER_COL}='{activity_id}'`——特征表按 `activity_id` 分区后这些查询吃到分区剪裁，人数口径=本活动特征行内命中；`1` 强制开、`0` 关闭回到全表口径。

**`MA_B_TIMEOUT` 要单独说。** 默认 1500 秒对方案 B 不够。7 月 28 日第一轮 B 就是卡在这上面：901 秒时 claude 报 `API Error: The operation timed out.`，整单 error，出参全空。跑通那轮实测 585.73 秒，`run_real_b.sh` 里已经写死 `export MA_B_TIMEOUT=3000` 留了一倍余量，**这个值不要再往回调**。

## 4. 圈人口径（最要紧的一段）

**这一节是 2026-07-29 改写的，老版本的说法作废。**

`ma_pipeline.py` 的 `pick_push_rules` 决定谁进人群包。有**两个互相独立的轴**，谁也不能替谁，混在一起想就一定会错：

**第一个轴是 `source`——决定这条规则圈不圈人。** 只有 `source == "audience_segment"` 的规则圈人，`diagnostic_rule` 是诊断结论、不圈人。而且必须带 `sql_filter`，没有 SQL 的圈不出人来。

**第二个轴是 `direction`——决定圈出来的人推不推。** 只有推送意图的规则会进出参，`exclude` 的只登记在 `excluded_rules` 里留个审计痕迹，不带 `sql_filter`、不参与 `push_sql`。这是你定的产品约束——"api 方式只会退出需要进行 push 的人群，需要排除的不会进行推送"。

**还有第三个东西叫 `push_source`，跟上面两个轴都无关。** `model` / `rule` / `both` 三选一，按 `finding_id` 前缀分：`fnd_model_*` 是模型产出，`fnd_r*` / `fnd_pos_*` 是规则产出。它决定的是"这一单要模型的还是规则的"，不是"推不推"。**2026-07-30 起它不再是入参**——调用方不能选了，由服务端 `MA_PUSH_SOURCE` 统一定，默认 `both`（产品口径是"要推的都给"；两轮真实联调也都是 both 跑的）。请求体里再带这个字段会被 400 拒单。

推送意图的识别不只认字面的 `push`。`PUSH_INTENT_RAW` 里列了一串：`push`、推送、触达、促付、促活、促转化、促成交、唤醒、召回、复购、承接、转化。`direction` 和 `direction_raw` 任一命中就算。命中的规则会把 `direction` 改写成 `push`，原值留在 `direction_from_skill` 里，同时在 `warnings` 记一条——改写了就得说，不能偷偷改。

`fnd_r41 创单未付待促付人群`就是靠这条捞回来的。skill 给它标的是"促付"，字面不是 `push`，早先的版本直接把它当排除人群扔了，这才是那次少了一批人的根因。

**认不出来的 direction 会被排除，但也会报警。** 比如"冷却"这种词不在名单里，规则会进 `excluded_rules`，同时 `warnings` 里留一条。不认识就静默丢掉是最坏的做法——人数少了没人知道为什么。

## 5. 报告产出链路（fix6 的主要改动）

方案 C 的流水线顺序是：`pull` → `prepare` → 回读品类核对 → `thresholds` → `draft` → `crowd_rules` → `crowd_push` → **`report_agent`** → `polish` → `self_critique` → `status` → `render` → `publish` → `assemble`。

`report_agent` 这一步是新加的。做报告的时候先给一个**带工具权限的 `claude -p`** 一次机会，让它自己去读 `SKILL.md`、自己跑 `marketing-audit` 把草稿做成定稿。它交出来的稿子接着当成新的草稿走后面那条链——该润的继续润，skill 自带的质检照跑，三道门禁一道不放过。

**它跑不成就原样用 `state_draft.json`，整条链跟 fix5 一模一样。** `run_report_agent` 有一整条守卫链，任何一环不满足就安静地返回"没用上"，**从头到尾不抛异常**：开关关了、诊断步骤不是 skill、`MA_CLI` 找不到、CLI 封装不支持工具、提示词拼不出来、调用抛异常、退出码非零、`state_full.json` 没生成、产物校验不过——九种情况，每种都退回老路。结果记在出参的 `backend.report_agent` 里，用没用上一看便知。

给它的提示词里明确写了两条禁令：**只许写 rundir 底下的文件**，**不许碰 skill 目录**。skill 是只读的，它的开关和子命令是拿来**调用**的，不是拿来**改**的。

**`--allow-channel-lint` 永远不许出现在 argv 里。** skill 自己的 `cli.py` 写着"仅用于调试，正式报告禁止使用"，方法论文档里也写了"不得使用"。有一条回归断言专门盯这个：这个词只能出现在注释、警告文案、或者带否定词的禁令里，一旦作为参数传出去就挂。

## 6. 接口出入参

`GET /healthz` 不鉴权，返回后端档位、claude 可用性、任务目录、并发上限。其余接口都要带 `x-ma-api-key` 头。

**这一节 2026-07-30 收窄过一轮，以下是现行契约。** 老版本入参里的 `push_source` / `pull_partition` / `campaign_type`（顶层）/ `note`，出参里的 `crowd_spec` 外壳 / `warnings` / `degraded` / `backend` 等，都不在对外契约里了。

`POST /api/ma/diagnose` 下单，同步返回 202，活计在后台线程跑。**入参只有三个键，多给的键 400 拒单（`E_BAD_PARAM`），不静默忽略**：`activity_id` 必填（字母数字下划线连字符，1–64 位）；`date` 选填（`YYYY-MM-DD`）；`meta` 选填（JSON 对象，`campaign_type`（≤64）放在这里面，还有 `campaign_name`、`target_products` 等）。202 的响应体是 `job_id` / `state` / `activity_id` / `mode` 四个字段。同一个 `activity_id` 在飞时再下单会被 409 `E_ACTIVITY_BUSY` 拒掉——同一活动跑两遍没有意义，还会互相覆盖产物。

```json
{ "activity_id": "356352",
  "date": "2026-07-29",
  "meta": { "campaign_type": "促转化", "campaign_name": "特价机票", "target_products": ["机票"] } }
```

`GET /api/ma/jobs` 列任务，`GET /api/ma/jobs/{id}` 查状态和日志流水（这条是轮询/运维接口，字段没收窄，`warnings` 和 `log_tail` 都在），`GET /api/ma/jobs/{id}/result` 取出参。终态只有 `done` 和 `error`。没跑完时 `/result` 返回 409 `E_NOT_READY`，失败 409 + 分步错误码。

**`/result` 成功时只有六个字段**：`job_id`、`state`、`activity_id`、`mode`、`report_url`（HTML 报告链接，发布失败时为 null）、`rules`（数组，**逐条只有 `name` / `finding_id` / `sql_filter` / `direction` 四个字段**）。

```json
{ "job_id": "job_...", "state": "done", "activity_id": "356352", "mode": "C",
  "report_url": "https://<网关域名>/diagnosis-report-356352.html",
  "rules": [ { "name": "创单未付待促付人群", "finding_id": "fnd_r41",
               "sql_filter": "...", "direction": "push" } ] }
```

**这个接口只出两样东西：报告链接 + 人群规则 JSON。** 不做任何表写入，不导入人群表，不落库。也**只输出需要推送的人群**。收窄砍的是出参不是记录：`push_sql`、`size.push`、`dropped_rules` / `excluded_rules`、`notes`、`degraded`、`warnings`、`backend`、`polish` 这些内部账全部还在 `jobs/<job_id>/meta.json` 里，排障照旧去那儿看（第 11 节）。要提醒一句：`degraded` 从出参里拿掉之后，调用方分不出"干净的一单"和"走了兜底的一单"，发布质量闸门（润色失败别裸发半成品报告）因此更要紧，别拖。

### campaign_meta 三个字段的兜底链(2026-07-30 定稿)

`--meta` 里**只放显式给的,不造占位符**——skill 的 `--auto-meta` 是"已提供字段不覆盖"的合并,提前塞占位值会把它从数据推真值的路堵死(356352 那单标题显示活动 ID 就是这个原因)。三条链,全部"入参 → 数据 → 兜底":

`campaign_name`:入参 `meta.campaign_name` / 环境变量 `MA_CAMPAIGN_NAME` → 数据的 **activity_name**(auto-meta 取众数)→ 兜底 `activity_id`(此时 warnings 会提醒"标题只能显示活动 ID")。报告大标题用的就是它。

`campaign_type`:入参 `meta.campaign_type` → 数据的 **activity_channel**(auto-meta 推到 target_channels,取第一个)→ 默认「**活动**」(老默认「社群进群」作废)。

`target_products`:入参 / `MA_TARGET_PRODUCTS` → 数据的 **activity_product_name**(见下节,取到页面名才报警)。

前两条的收尾兜底在 `apply_meta_defaults`(prepare 之后执行,run.log 里会写明每个值的来源),最终 `campaign_type` 会同步给报告产出 Agent 的提示词。

### `target_products` 的口径

`target_products` 是**品类名**。有两条路，**两条都是正常路径**：

**默认**——不传就走 `--auto-meta`，从数据的 `activity_product_name` 里取。这是常规走法，**不报警**。取到了什么会写进出参的 `notes`，想看就看一眼。

**指定**——下单时 `meta.target_products` 传数组，或者 `export MA_TARGET_PRODUCTS='机票,酒店'`。

只有一种情况会在 `warnings` 里吵一声：`prepare` 之后回读实际取到的值，发现它**看着像页面名**（"特价机票业务总览"这种）而不是品类名。这时候"跨品类推送错配"那类结论就不能直接采信，得人先确认。

早先的版本是"没显式传就警告"，改掉了。默认路径不是降级，每一单都顶着一条假警报，久了谁都不看 `warnings` 了。该盯的是**实际取到的值对不对**，不是**有没有显式传**。

## 7. 门禁与降级标志

三道门禁，退出码分得清清楚楚，别混：

**schema 错误 → exit 2，硬失败。** 结构不对就是不对，不放行。

**lint 警告 → 不拦。** 它的显示格式跟 schema 错误长得一样（比如"headline 长度 26 字 < 30 字"），容易看岔，但它不阻断。

**完备性 `INCOMPLETE_REPORT` → exit 4。** 正文还是草稿骨架句。兜底是改用 skill 自己的 `--skip-completeness` 强制产出，同时在 `warnings` 里如实写明"样式为正版模板，正文可能仍残留草稿骨架句"，并把 `render_forced` 置真。

**渠道 `REWRITE_REQUIRED` → exit 3。** 触发重写，最多试 `MA_CHANNEL_TRIES` 次。

`degraded`、`skill_degraded`、`render_forced` 三个标志位是有意留的：任何一个为真，都说明这一单走了兜底路径，出参可以用但要人看一眼。全为假才是干净的一轮。

**降级横幅（2026-08-03 新增）**：润色未完成、又没有 agent 成品兜底时，**发布出去的报告页顶部会压一条置顶橙色横幅**（"文案润色未完成×N 处，发给业务方前请人工复核"）——出参里的 degraded 标志读者看不见，压在页面上的字才看得见。`report_url` 照给、规则照出，rundir 里的原件不动，只有发布副本带横幅。

Prism 占 8080 / 3001。方案 C 用 **8092**、方案 B 用 **8093**，两个都只绑 `127.0.0.1`——设计如此，不要改成 `0.0.0.0`。报告静态服务在 **8000**，绑的是 `0.0.0.0`，但轻量服务器的防火墙只放通了 22 和 3001，所以 `report_url` 里那个 `http://43.167.214.72:8000/...` **从外网打不开**。

## 9. 上公司 ma_server（反代 + 自启）

前面八节说的都是下午那台测试机。真正要交付的是公司 ma_server，那台机器有三处根本不同，而且**三处配错了都不报错**——接口照样 200、照样返回 `report_url`，只是那个链接在公司网里点不开。所以这一节的每一条，`preflight_ma_server.py` 里都有对应的检查。上机第一件事是跑它，不是起服务。

### 9.1 端口：为什么必须走反代

公司网关 `https://friday_deployment_14540_algo_agent.gw.friday.17usoft.com` **只转发 8080**，而 8080 是 Prism 的。诊断服务自己开一个 8092 对外，网关根本不认——从公司网发过去的请求到不了。

解法不是去申请端口，是把接口挂到 Prism 底下：Prism 在 8080 上收到 `/api/ma/*`，转给本机回环的诊断服务。对外只有一个端口、一个域名，和 Prism 同源。

在**起 Prism 的那个 shell** 里：

```bash
export PRISM_MA_API_TARGET=127.0.0.1:8092      # 方案 C;方案 B 是 8093
export PRISM_MA_API_TIMEOUT_MS=120000          # 可选,默认 120 秒
export PRISM_MA_API_MAX_BODY=262144            # 可选,默认 256 KB
```

**不配 `PRISM_MA_API_TARGET`，反代根本不挂载**——这是默认，也是有意的：没人配它的时候，Prism 不该凭空多出一条路由。

三条硬性限制，都是代码里拒绝而不是文档里劝阻：目标**只认回环地址**（`127.0.0.1` / `localhost` / `::1`），能转到任意主机的反代就是一个现成的 SSRF 跳板；路径是**精确白名单**，不是前缀通配；转发前会把 Prism 自己的 `Authorization`、`Cookie`、`x-prism-api-key` **摘掉**，诊断服务只认自己的 `x-ma-api-key`。

于是对外调用长这样：

```bash
curl -X POST https://<网关域名>/api/ma/diagnose \
  -H 'content-type: application/json' \
  -H "x-ma-api-key: $MA_API_KEY" \
  -d '{"activity_id":"...","meta":{...}}'
```

### 9.2 自启：起 Prism 就把诊断服务带起来

不想每次开两个终端的话，让 Prism 顺带把它拉起来：

```bash
export PRISM_MA_API_AUTOSTART=/home/jovyan/prism/ma-api-mode/ma_api_c.py   # 必须绝对路径
export PRISM_MA_API_PYTHON=python3          # 可选,默认 python3
```

一条 `npm start` 起两个进程，Prism 退出时子进程一并收掉（先 SIGTERM，4 秒不走再 SIGKILL）。子进程崩了会按退避重启，最多 5 次；起来后先探 `/healthz` 才算成功；它的 stdout/stderr 被逐行转写进 Prism 的日志，每行带 `[ma-service] |` 前缀，`grep` 这个就能把它单独捞出来。端口上要是已经有人在应答，Prism 认为那是外部起的，既不重复拉起、退出时也不收。

这里有一个刻意设计的性质：**子进程监听哪个端口，是从 `PRISM_MA_API_TARGET` 反推的，不读你 shell 里的 `MA_API_PORT`。** 换句话说反代和服务两边配歪这件事从根上就不存在了——不是"配歪了会警告"，是配不歪。

两条会**拒绝自启**（是不起，不是起了之后警告一声）：

- 没设 `MA_API_KEY`。这条路径是经网关对外的，裸跑等于把接口敞开。本机调试才用 `PRISM_MA_API_ALLOW_NO_KEY=1`，那时候会起，但会明确告诉你没有鉴权。
- `MA_API_KEY` 和 `API_KEY` 同值。`API_KEY` 是 Claude Code CLI 的凭据，而两个服务调 `claude` 时都是 `env=os.environ.copy()` 整个环境传下去的——把接口口令和模型凭据设成同一个串，等于让每个调接口的人都拿到了后者。

还有一条最容易踩：**`MA_*` 那一堆变量要 `export` 在起 Prism 的 shell 里**。子进程继承的是 Prism 的环境，不是你后来另开的那个终端的。

### 9.3 报告链接与取数

`MA_PUBLIC_DIR` 和 `MA_URL_BASE` 在 `real` 档下的出厂默认值已经是 ma_server 的正确值（`/home/jovyan/prism/public` + 网关域名），正常情况下不用配。会出事的是**从测试机复制 `export` 过来**：`MA_URL_BASE=http://43.167.214.72:8000` 带到 ma_server 上，接口会照常返回成功，而链接指向一台公司网里根本不存在的机器。体检把这条列为致命，服务会拒绝启动。

取数走 `MA_RUNTIME=real`（Hive）。**这条路径至今没有在任何机器上真跑过**——测试机上不去数仓，云端更没有。`preflight_ma_server.py` 能查的只是"取数脚本在不在、发布目录在不在"，查不了"这张表你有没有权限"。第一单必须盯着 `pull` 那一步的日志看。

### 9.4 上机顺序

```bash
cd ~/prism/ma-api-mode                    # 以实际部署路径为准
python3 preflight_ma_server.py            # 先体检。✗ 必须清零,⚠ 逐条看过再决定
ACT=真实活动ID bash run_ma_server.sh c    # 整轮联调:起服务→下单→轮询→打印出参→核对发布物
```

`ACT` 不给会直接拦住，不会用一个假 ID 往下跑：`real` 档是照着 `activity_id` 去 Hive 捞人的，随手编一个不报错，只会捞回 0 行，然后一路顺利地产出一份"什么都没发现"的报告——那种结果比报错难查得多。

`run_ma_server.sh` 会先探端口：**已经有服务在应答就复用，不抢。** 因为那个进程很可能是 Prism 自启的子进程，`pkill` 掉它 Prism 会立刻按退避策略再拉起来，而脚本自己也起了一个，两个进程抢同一个端口，后起的 bind 失败退出、再被拉起、再失败……日志会很热闹，但你要的那一单一直下不出去。真要让脚本自己起，`FORCE_RESTART=1 bash run_ma_server.sh c`；但如果端口上那个确实是 Prism 的子进程，正确做法是**重启 Prism**，不是在这儿 kill。

## 11. 排障备忘

服务起不来先看日志头部，导入期的报错都在那里：测试机上是 `c_real.log` / `b_real.log`，ma_server 上手工起的是 `c_ma_server.log` / `b_ma_server.log`。Prism 自启的那份**没有独立日志文件**——它的 stdout/stderr 被逐行转写进 Prism 的日志，每行带 `[ma-service] |` 前缀，`grep 'ma-service'` 捞。`run_ma_server.sh` 复用现成服务时也不会有日志文件，脚本最后会明说这一点，别对着"文件不存在"发呆。任务卡住看 `jobs/<job_id>/meta.json` 的 `phase` 和 `logs`，每一步都有时间戳。产出不对先看 `warnings` 和 `contract_repairs`，降级路径都会在那里留痕。

报告产出 Agent 没用上，看 `backend.report_agent` 里的 `reason` 字段，九种退回原因每种都有对应的字符串。它的原始输出留在 rundir 的 `agent_stdout.txt` 和 `agent_prompt.txt`。

CSV 编码这次是 GB 系，脚本里写死 `gb18030` 读。换数据源时如果 `MA_CSV_ENCODING` 设错，症状是取数阶段直接抛解码异常，不会静默出错。

环境变量改了不生效，十有八九是没 `export` 就起进程，或者 `export` 写在 `python3` 后面了。第 3 节开头那句不是客套话。

`jobs/` 目录会一直堆积，每单一个子目录，带完整的 run 产物。磁盘紧张时可以按日期清理，但**清之前确认没有正在跑的单**。
