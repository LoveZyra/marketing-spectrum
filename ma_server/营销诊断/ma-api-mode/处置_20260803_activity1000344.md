# 处置方案:activity 1000344 报错(2026-08-03,不改代码版)

配套阅读:《诊断_20260803_activity1000344.md》(根因三层:prepare 被 SIGKILL 疑似 OOM → 降级骨架撞上不存在的人群池表 → fallback 无兜底,裸 traceback)。本文回答两件事:**"我不圈人,为什么还要这张表"**,以及**不改代码怎么处置**。

## 一、"我不圈人,为什么还要这张表"

短答:**代码在消费它,不是你在消费它。** 这份 ma_pipeline.py 没有"只诊断、不圈人"的模式,POP_TABLE(人群池表)在三处被无条件用到——以下均已在本地代码里逐条核对,不是推测:

1. **主链路 crowd_push 步是无条件的。** run_pipeline 里 `ctx.step("crowd_push", _crowd)` 固定执行:validate_rules 逐条 `LIMIT 0` dry-run、count_rules 一趟 `SUM(CASE WHEN)`、count_push_total `COUNT(DISTINCT mapid)`——三类查询全部 `FROM POP_TABLE`。环境变量全表(MA_*)里没有任何一个能跳过这一步。

2. **出参契约写死了它。** `crowd_spec.push_sql` 的 FROM、`source_table`、`data_source` 都取自 POP_TABLE(BaseSource.label / sql_table)。这一处只用表名、不查库,倒是不炸,但说明"圈人字段"在契约里不是可选项。

3. **降级骨架借它取"真列"。** hive runtime 下 skill 任何一步失败都退回本地骨架;骨架的设计是"假规则也要长在真实存在的列上、阈值取真分位数",而 HiveSource 把"真列"实现成查**人群池表**(describe_columns → `spark.table(POP_TABLE)`),不是查已经拉到本地的 data.parquet。**这单就是死在这里。**

表不存在时的行为差别:路径 3 直接崩(未捕获 AnalysisException,即本单);路径 1 不崩,但每条规则会以同样的表错误被逐条剔掉、size.push=0——单"成功",圈人部分全废,还白跑几个 Spark 作业。

所以:只要还在这份代码上跑 hive runtime,POP_TABLE 就必须指向一张**存在**的表,与你用不用圈人无关。想真正解耦,要加"只诊断"开关,那属于改代码(见 §四 第 1 条)。

## 二、今天就做(两个 export + 重启)

在**起 ma_api 服务的环境**里(jovyan;写进启动脚本,别只在临时 shell 里敲,服务一重启就丢):

```bash

#    备选:老样本表若还在 → export MA_POP_TABLE=tmp_dm.tmp_ctj_mktv2_sy_sample
```

为什么推荐 hebo 特征表:pull 刚在它身上成功过,存在性是实测的;你不消费圈人出参,"计数口径变成该活动特征行内命中"对你无感;等数仓把 `app_dm.long_ctj_marketing_audit_sample` 真建出来,删掉这行 export 就回到正式口径。代价:降级分位数查询和 crowd_push 计数会在这张表上多跑几个 Spark 作业,大活动多花几分钟——反正结果你不用,只是时间成本。

## 三、重跑后会发生什么(预期,别被"成功"骗了)

做完 §二重跑 1000344,预期链路:pull ~15 分钟 → **prepare 大概率仍被 SIGKILL**(OOM 没治)→ 降级骨架,这次 describe_columns 在 hebo 上成功 → 骨架规则 + 真分位数 → crowd_push 在 hebo 上计数 → 报告正常产出。

也就是:**单不死、report_url 有,但 degraded=true,报告是骨架质量**(占位文案 + 分位数造的规则)。要"真报告",必须接着治 OOM——这才是主矛盾。按代价从小到大:

1. **给 jovyan 容器加内存配额**(最直接)。先上服务器拿证据:

```bash

cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory.events 2>/dev/null    # 看 oom_kill 计数
# 复现内存峰值(另开窗口 free -m 盯着):
python3 -c "import pandas as pd; df=pd.read_parquet('<上面那个data.parquet>'); print(df.shape, round(df.memory_usage(deep=True).sum()/2**30,2), 'GiB')"
```

2. **数仓侧瘦身**:特征表只保留诊断用到的列,或对超大活动预聚合(数据小了,OOM 和 15 分钟拉数一起缓解)。

3. **取舍开关**:`export MA_SKILL_STRICT=1` —— 宁可整单明确报 E_PREPARE_FAILED,也不要骨架报告。适合"骨架报告可能被当成真结论发出去"的场景;不适合"有个报告总比没有强"。

## 四、哪天愿意改代码了(按"我不圈人"重排优先级)

1. **加"只诊断不圈人"开关**(跳过 crowd_push、圈人出参字段置空)——对你的用法是根治:POP_TABLE 从此与你无关,连 export 都不用。
2. `_try` 给 fallback_fn 也套 try/except,任何异常转结构化 StepError(如 E_FALLBACK_FAILED),接口永不吐裸 traceback。
3. describe_columns/quantile 在 POP_TABLE 不存在时降级读本地 data.parquet(读 schema 零内存、分位数按单列读),骨架路径与人群池表彻底解耦。
4. run_cmd 对负 returncode 标注信号名(-9 → SIGKILL,提示疑似 OOM);pull 完打点 data.parquet 体积,"数据多大 → 有没有被杀"在日志里一眼可对。

其中 2–4 与《诊断_20260803_activity1000344.md》§四一致;第 1 条是按"我不圈人"新提的,建议排最前。
