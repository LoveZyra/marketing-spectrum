# 诊断结论:activity_id=1000344 这单为什么报 E_INTERNAL(2026-08-03 15:15 单)

结论一句话:**skill 的 prepare 被 SIGKILL(疑似 OOM)触发降级,降级骨架去查人群池表
`app_dm.long_ctj_marketing_audit_sample` 取列名,这张表在 metastore 里不存在,抛出的
`AnalysisException` 没有任何一层接得住,整单以"未捕获异常"收场。** 三层问题叠加,缺一不炸。

本文档只做诊断与建议,未改动任何代码。行号以线上 traceback(/home/jovyan 部署版)为准,
本地 marketing-spectrum 这份与之相差约 4~5 行。

## 二、因果链(三层)

### 层 1(诱因):prepare 被 SIGKILL,高度疑似 OOM

证据:

- exit=-9 即 SIGKILL。不是流水线自己杀的:run_cmd 的超时(MA_STEP_TIMEOUT 默认 1800s)
  走的是 `subprocess.TimeoutExpired` 分支,报的是"子命令超时",不会出现 -9;138 秒也远没到超时线。
- **prepare 一行 stdout 都没吐出来。** cli.py 进 `cmd_prepare` 第一件事就是
  `print(f"[prepare] reading {args.data}")`(cli.py L177),但日志里 `$ python3 ... prepare` 和
  ⚠ 降级之间一行 `|` 都没有,skill_error 落盘也是空的——非 tty 下 Python stdout 是块缓冲,
  进程被 SIGKILL 时缓冲区直接蒸发。典型的"被外力秒杀"现场,而不是自己抛异常退出。
- 杀点在数据装载附近:cli.py 的 `_load_dataframe` 是 `pd.read_parquet(path)`(L52-56)
  **一次性整表进内存**,拉数跑了 15 分钟的活动切片,解压成 pandas 内存态很容易翻几倍。
  jovyan 是容器环境,撞 cgroup 内存上限就是 kernel OOM killer 直接 kill -9,不留遗言。

如何坐实(上服务器执行):

```bash
# 1) 这单的数据到底多大
ls -lh /home/jovyan/prism/ma-api-mode/jobs/job_20260803_151501_8c21ce/run/data.parquet

# 2) 内核/容器有没有 OOM 记录
dmesg -T 2>/dev/null | grep -iE "killed process|oom" | tail
cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes 2>/dev/null
cat /sys/fs/cgroup/memory.events 2>/dev/null   # oom_kill 计数

# 3) 手动复现(建议先 free -m 盯着)
python3 -c "import pandas as pd; df=pd.read_parquet('.../data.parquet'); print(df.shape, df.memory_usage(deep=True).sum()/2**30, 'GiB')"
```

### 层 2(引爆点):降级骨架必须查 POP_TABLE,而这张表不存在

- 降级链路:`_try`(L1115)捕获 E_PREPARE_FAILED → `StubSteps.prepare`(L1313)→
  `build_stub_state`(L1499)→ `_pick_numeric`(L1467)→ `HiveSource.describe_columns`(L539)
  → `spark.table(POP_TABLE).dtypes` → 表不存在,炸。
- 骨架的设计是"假规则也要长在真实存在的列上、阈值取真分位数"(build_stub_state 的 docstring)。
  对 HiveSource 来说,"真列"被实现成了查 **人群池表**,而不是查已经拉到本地的 data.parquet——
  所以即便完全不消费圈人结果,走到降级路径也绕不开这张表。
- `POP_TABLE` 的默认值 `app_dm.long_ctj_marketing_audit_sample` 是 **2026-08-03 当天刚落定的新值**
  (ma_pipeline.py L115-117 注释:"人群池表(2026-08-03 与特征表一起落定)"),
  启动侧也没有 `MA_POP_TABLE` 覆盖——即默认值直接上线,但 metastore 里这张表还不存在
  (未建成/名字有出入/库名不同,需与数仓对一下)。同日落定的特征表 hebo 是存在的(pull 成功)。

顺带说明"我不用圈人,为什么要查它":现在的代码没有"只诊断、不圈人"的模式。
除了上面这个降级取列的用途,`run_pipeline` 主链路里 `crowd_push` 步(validate_rules L~561 /
count_rules L~574 / count_push_total L~585,均 `FROM POP_TABLE`)是无条件执行的,
出参 `crowd_spec.push_sql / source_table` 也引用它。这单如果没死在层 2,
后面也会在 crowd_push 把所有规则以同样的表错误逐条剔掉、size.push=0(不炸,但全废)。

### 层 3(为什么是"未捕获异常"而不是体面报错)

`_try`(L1115-1120)只捕获 **real_fn 抛的 StepError**;fallback_fn 抛的
`pyspark AnalysisException` 不在保护范围,一路穿透 step → run_pipeline,
最后被 ma_core.`_run_job` 的兜底 `except Exception`(ma_core.py L514-520)记成
`E_INTERNAL` + 裸 traceback。与"MA_SKILL_STRICT=0 时任何一步降级不致死"的设计初衷相悖——
兜底路径自己没有兜底。这是一个真实的健壮性缺口,值得哪天顺手补上(本次按要求不动代码)。

## 三、不改代码的处置办法

**① 让这单不再死:给 MA_POP_TABLE 指一张存在的表。** 在起服务的脚本里加:

```bash
export MA_POP_TABLE=app_dm.tmp_ctj_marketing_audit_features_hebo   # 用特征表当人群池
# 或者,若老表还在:export MA_POP_TABLE=tmp_dm.tmp_ctj_mktv2_sy_sample
```

然后重启服务。注意事项:不消费圈人出参的话口径变化对你无感;若消费,计数含义变为
"该活动特征行内的命中",push_sql 的 FROM 也会写这张表;主键列若不叫 mapid/unionid,
用 MA_ID_COL / MA_UNION_COL 配平;降级路径的分位数查询会在这张表上跑若干个 Spark 作业,
大表会多花几分钟。等数仓把 `app_dm.long_ctj_marketing_audit_sample` 真建出来,去掉这行即可。

**② 让报告质量回来:解决 prepare 的 OOM(这是主矛盾)。** 表修好只保证"单不死";
prepare 继续被杀的话,每单都是骨架报告(degraded=true,占位文案+分位数造的规则)。
可选路径按代价从小到大:给 jovyan 容器加内存配额;让数仓把特征表按需瘦身
(只保留诊断用到的列,或对超大活动预聚合);实在要保产出,接受降级但先按 ① 把表指对。

**③ 两个顺手的运维开关(都不用改代码):**

```bash
export PYTHONUNBUFFERED=1   # 子进程 print 实时落日志,下次再被杀能看到死前走到哪一步
# export MA_SKILL_STRICT=1  # 可选:宁可整单报 E_PREPARE_FAILED 也不要骨架报告时再开
```

## 四、如果哪天愿意改代码(备忘,按收益排序)

1. `_try` 给 fallback_fn 也套 try/except,任何异常转成结构化 StepError(如 E_FALLBACK_FAILED),
   接口永远不再吐裸 traceback;
2. `HiveSource.describe_columns/quantile` 在 POP_TABLE 不存在时降级读本地 data.parquet
   (列名读 schema 零内存,分位数按单列读),骨架路径彻底与人群池表解耦;
3. `run_cmd` 对负数 returncode 标注信号名并提示"疑似 OOM";pull 完打点 data.parquet 体积,
   让"数据多大→有没有被杀"在日志里一眼可对;
4. 加"只诊断不圈人"开关(跳过 crowd_push、出参圈人字段置空),与你的实际用法对齐。
