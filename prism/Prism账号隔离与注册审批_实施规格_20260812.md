# Prism 账号隔离与注册审批 · 实施规格

> 2026-08-12。目标:**同事之间别互相点错、界面清爽**;不同同事不同账号;注册由 root 审批。
> 明确不做:防越权(知道 id 直接调接口仍可访问)。这一点必须写进用户可见的说明里,
> 不能让人误以为已经隔离——真隔离需要 OS 级方案,见《Prism功能增强方案》D 节。

## 已锁定的三个决定

| 决定 | 选择 |
|---|---|
| root 认定 | **指定用户名,env 配置**:`PRISM_ROOT_USERS=tianji.chang`(逗号分隔多个) |
| 存量项目归属 | **全部归 root**,其他人看不到 |
| 公共项目 | **保留**,`owner_user_id IS NULL` 即公共,所有人可见可用 |

root 身份**不落库**,每次从 env 现算(`username ∈ PRISM_ROOT_USERS`)。好处:换人只改配置,不必改库,也不会出现"库里标了 root 但 env 里没有"的状态分裂。

## 数据结构

```sql
-- users:审批三件套。默认 'approved' 是关键 —— 存量账号一个都不受影响。
ALTER TABLE users ADD COLUMN approval_status TEXT NOT NULL DEFAULT 'approved';  -- pending|approved|rejected
ALTER TABLE users ADD COLUMN approved_at DATETIME;
ALTER TABLE users ADD COLUMN reviewed_by INTEGER;   -- 审批人 user id,留痕

-- projects:归属。NULL = 公共项目。
ALTER TABLE projects ADD COLUMN owner_user_id INTEGER;
```

`schema.ts` 里的 CREATE TABLE 同步加上这几列(新装环境直接带),`migrations.ts` 加 ALTER(存量环境补齐),两边保持一致。

### 存量项目归 root 的时机

迁移只加列,**不在迁移里赋值** —— 迁移跑的时候 root 账号可能还不存在。改为启动时的一次性回填:

1. 从 `PRISM_ROOT_USERS` 取第一个**在库中存在**的用户名,拿到 user id;
2. 查 `app_config` 里有没有 `projects_owner_backfilled` 标记,有则跳过;
3. 没有则 `UPDATE projects SET owner_user_id = <rootId> WHERE owner_user_id IS NULL`,写入标记。

root 账号还没注册时跳过、下次启动再试。标记只写一次,所以 root 之后把某个项目设成公共(owner 置 NULL)不会被下次启动重新抢回去。

## 行为规格

### 注册

- 新注册账号 `approval_status='pending'`;若用户名在 `PRISM_ROOT_USERS` 里,直接 `approved`。
- 注册成功的响应要明说"已提交,等待管理员审批",不要让人以为能直接登录。

### 登录

判定顺序(顺序很重要):

1. 用户名/密码校验 —— 不通过按现有逻辑返回;
2. **root 直接放行**,不看 `approval_status`(防止 root 自己被锁在外面);
3. `PRISM_APPROVAL_REQUIRED=0` 时跳过审批检查(**逃生开关**,见下);
4. `approval_status='pending'` → 403 `待管理员审批`;`'rejected'` → 403 `注册申请未通过`。

### 审批接口(仅 root)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/users` | 列出所有账号:用户名、状态、注册时间、审批人、审批时间 |
| POST | `/api/admin/users/:id/approve` | 置 approved,记 `approved_at` 与 `reviewed_by` |
| POST | `/api/admin/users/:id/reject` | 置 rejected,同样留痕 |

统一走一个 `requireRoot` 中间件;非 root 一律 403。审批动作写 `audit_log`(表已存在)。

### 项目可见性

- **列表**:非 root 只返回 `owner_user_id = <me> OR owner_user_id IS NULL`;root 返回全部。
- **新建/克隆**:`owner_user_id` 设为当前用户。
- **归属变更**:root 可以把项目转给别人或设为公共(`PATCH /api/projects/:id/owner`,入参 `{ ownerUserId: number | null }`)。
- **会话**:通过 `sessions.project_path → projects` 推导归属,不单独加字段。无项目归属的会话按公共处理。

### 这一档**不做**的事

各个 project 级接口(files / git / checkpoints / taskmaster …)**不加归属校验**。知道 `projectId` 的人照样能调。这是刻意的取舍:改全那些接口是 1–2 周的工作量,而当前诉求是"别互相点错"。

## 防锁死的三道保险

改登录链路最大的风险是把所有人关在门外,所以:

1. **列默认值 `'approved'`** —— 存量账号迁移后状态不变,照常登录。
2. **root 绕过审批检查** —— 即使审批逻辑写错,配了 `PRISM_ROOT_USERS` 的人也能进。
3. **`PRISM_APPROVAL_REQUIRED=0`** —— 整个审批闸门可以一键关掉,退回改动前的行为。上线前先用它验证"关掉时一切如常",再打开。

另外**迁移必须可回滚**:SQLite 不支持 DROP COLUMN(旧版本),但多出来的列对老代码无害——回滚只需换回旧的 `dist-server`,库不用动。

## 验证清单

上线前按顺序跑,每步都要过:

1. `PRISM_APPROVAL_REQUIRED=0` 启动 → 所有存量账号照常登录,项目列表与改动前一致(**先证明没破坏现状**);
2. 打开审批 → 存量账号仍能登录(默认 approved 生效);
3. 新注册一个账号 → 提示待审批,登录被拒且文案清楚;
4. root 登录 → 看到待审列表 → 批准 → 该账号能登录了;
5. 拒绝另一个账号 → 登录被拒,文案与待审不同;
6. 非 root 调 `/api/admin/users` → 403;
7. 存量项目回填后:root 看到全部,新账号看到空列表(**符合"全部归 root"的选择**);
8. root 把一个项目设为公共 → 新账号能看到了;
9. 新账号自己建一个项目 → 只有他和 root 看得到;
10. 重启服务 → 回填不重复执行(标记生效),第 8 步设的公共项目没被抢回去。

第 7 步会让新账号第一次登录看到空列表 —— 这是你选的方案的预期行为,记得跟同事说一声,不然会当成 bug 报过来。

## 工作量

后端约 1 天,前端(审批面板 + 归属标记)约半天,验证半天。合计 **2 天**。

建议分两次上:先上后端 + 逃生开关(默认关闭审批),验证零破坏;再打开审批并上前端面板。
