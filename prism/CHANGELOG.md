## 2026-08-27 · cy — 算法效果查询改成常驻入口

用户报:方案咨询卡里看不到"算法效果查询"。

不是 bug,是 cx 的设计在挡路。cx 让前端先问 `GET /api/integrations`,
反代没挂就不显示这个入口 —— 出发点是"没配 `PRISM_RECSYS_TARGET` 的部署里,
点进 `/recsys` 会掉进 SPA 的 catch-all,看到 Prism 自己的界面套在一个奇怪地址上,
比 404 还难懂"。用户那台机器没配这个变量,于是入口整个消失了。

用户要的是**入口一定在**。那就不能靠藏,得把当初怕的那件事本身修掉:

- **`/recsys` 没配时由服务端接住**,返回 503 和一页人话:「算法效果查询还没接上」
  + 该在 `.env` 里加哪一行 + 上游要配 `HOST=127.0.0.1`。不再掉进 SPA 的
  catch-all。启动日志也相应打一句「未配置…会给出配置提示页」。
- 既然这条路有人接了,**入口就无条件展示**,`href` 直接写 `/recsys`。
- 于是 `GET /api/integrations`、`api.integrations()`、组件里那段 fetch 全部删掉 ——
  它们唯一的用途就是决定显不显示,现在不需要了。

### 方案咨询卡

按用户的意思**删掉一个原始例子**(「这个排序场景该选什么模型,讲讲权衡」),
只留「推荐一个适合冷启动推荐的算法方案」+「算法效果查询」。
这样这张卡也是两行,和其余三张齐平,链接不会把卡片撑高。

验证:typecheck 双端过;eslint 0 错误(46 warnings 基线);vitest 874 全过;
双端构建过。浏览器探针**两种部署形态各跑一遍,各 7 项全过**:
- 没配 `PRISM_RECSYS_TARGET`:四张卡都在、**链接照常展示**、点击落到配置提示页
  (而不是 Prism 界面)、提示页写明了要配的变量、0 pageerror。
- 配了:链接展示、点击真落到 recsys 页面、地址含 `/recsys`、0 pageerror;
  302 的 `Location` 仍被改写成 `/recsys/login`。

## 2026-08-27 · cx — recsys 反代进主干 + 起始卡片改版

用户线上把 recsys(推荐算法点位监控)手工挂在了 Prism 的 `/recsys` 下 ——
自己写了 `server/routes/recsys-proxy.js`,又手改了 `server/index.js` 和
`dist-server/server/index.js` 的挂载。这个做法有个必然的结局:**下次升级
`tar --overwrite` 会把 `server/index.js` 盖掉,挂载消失**,而 `recsys-proxy.js`
因为 tar 不删文件会留下来,变成一个谁都不引用的孤儿文件 —— 服务照常起,
`/recsys` 静悄悄 404。所以这轮把它收进主干。

### recsys 反代

- 新增 `server/routes/recsys-proxy.js`,挂载点写进 `server/index.js`。
  **`PRISM_RECSYS_TARGET` 不配就整层不挂载**,对没有这个服务的部署逐字节无影响。
- 与 ma-proxy 的两点区别,都是被上游的形态逼出来的:
  - **不做路径白名单**。ma-proxy 的下游是五个能精确列举的接口;recsys 是一整个
    前端页面(HTML/JS/CSS/data/*.json),路径是上游自己长出来的,列不完。
    代价写在文件头上了:上游多出什么接口这里就跟着暴露什么,所以只往这挂
    "整站公开只读"的服务。
  - **改写 Location**。上游在回环上挂在根路径,它发的 302 指向 `/login`;
    浏览器会跳到 Prism 的 `/login` 而不是 `/recsys/login` —— 直接跳出反代,
    落到 Prism 自己的前端路由上,表现为莫名其妙的白页。往回走的 Location
    补前缀,绝对地址和相对路径都不动。
- 少了白名单之后,路径检查只剩 `hasTraversal` 一道,比对**未解码**的原始路径
  (`%2e` 直接拒)。写测试时发现 `fetch` 会先把 `%2e%2e` 归一化掉,请求根本
  到不了这层 —— 也就是说这道闸防的不是浏览器,是 `curl --path-as-is` 那类
  原样发包的客户端。测试因此改用 `http.request` 直接发原始路径。
- 额外带 `X-Forwarded-Prefix: /recsys` 下去,让上游能自推导对外前缀,
  而不是把 `/recsys` 硬编码进模板。

### 反代骨架抽公共

`ma-proxy` 里那套"只转回环 / 剥逐跳首部 / 剥 Prism 凭据 / 补 X-Forwarded-*"
抽成 `server/routes/proxy-kit.js`,两个反代共用。

反代文档原本教的是 `cp recsys-proxy.js myapp-proxy.js` 再改名字。复制粘贴的
问题不在写的时候,在改的时候 —— 哪天回环判断要补一条(比如某种新的 IPv6
写法),复制出去的那几份不会跟着变,而且没有任何东西会提醒你它们存在。
文档把这几条称作"不可绕过"的硬约束,那就不该靠复制来维持。

只抽**判断和拼装**,没抽转发循环:ma-proxy 那圈 pipe 带着一段和 Python 上游
有关的 `agent:false` 来龙去脉,recsys 要做的又是改 Location、不做白名单,
两边的循环本来就不一样,硬合成一个再用参数区分,那就白抽了。
`ma-proxy.js` 315 → 235 行,`parseUpstream` / `buildUpstreamHeaders` 原样再导出
一次,它的 21 个测试一个字没改就全过。

### 起始卡片

- **场景诊断 → 分析专家**,两个例子换成"外部专题调研"和"内部业务经营分析"。
- **删掉数据分析、算法模型两张卡**,剩四张:营销活动诊断 / 分析专家 / 算法建模 / 方案咨询。
- **方案咨询里挂"算法效果查询"入口**,点了新标签页打开 `/recsys`。

链接不是写死的。前端先问 `GET /api/integrations`,反代没挂就不显示这个入口 ——
写死的话,没配 `PRISM_RECSYS_TARGET` 的部署点进去会掉进 SPA 的 catch-all,
看到的是 Prism 自己的界面套在一个奇怪的地址上,比 404 还难懂。

## 2026-08-27 · cw — G1 测试补齐 + G3 分包(路线图收尾)

### G1 · 把没有测试的那几处补上

**鉴权中间件(此前一个测试都没有)。** 它是整个服务里唯一决定"你是谁、能不能进"
的地方,而任何一条判据错掉都是越权 —— 越权是这类系统里最贵的错。15 个用例覆盖:
没带 token / 伪造签名(401 与 403 的区分)、token 指向的用户不存在、
**token_version 一变旧 token 全废**(改密码与全端登出的实现)、停用账号进不来、
root 身份来自 `PRISM_ROOT_USERS` 而不是数据库列、默认拒绝 `?token=`
(那正是要消灭的泄漏面)、`PRISM_ALLOW_QUERY_TOKEN=1` 的老部署才放行、
API key 闸(含"长度不同的 key 不会让 `timingSafeEqual` 抛出来" —— 它对不等长会抛)、
WebSocket 升级鉴权与 REST 同口径。

**注册/登录路由。** 用一个真的 express 服务器跑真的 HTTP —— 中间件顺序
(限流 → 锁定 → 路由)本身就是被测对象,拿函数单独调测不出来。10 个用例覆盖:
第一个账号免审批(全新安装时没有任何人能来批它)、之后的账号进待审队列
**且不发 token**(登不进去的账号不该拿到会话)、root 免审批、
**不存在的用户与密码错误给同一句话**(否则登录框就是用户名探测器)、
连续失败锁定后连正确密码也进不去、锁的是 (IP, 用户名) 而不是账号本身。

**`resolveVisibleProjectRoot` 契约。** 它是所有按 projectId 寻址的路由的第一道门
(文件读写、上传、预览、全局搜索……),一旦对不该看见的项目返回了路径,后面每条
路由都会照着那个路径去读写。7 个用例覆盖五种可见性形态 + 不存在/空/路径穿越形状的 id。

**checkpoint 还原。** 打 checkpoint 有测试,还原一直没有 —— 而还原才是危险的那半:
它 `git reset --hard`、删未跟踪文件、replay stash。7 个用例,钉的都是**拒绝**与
**兜底**:之后有提交时默认拒绝并列出提交(且被拒绝时工作区一个字节都不动)、
快照不完整时默认拒绝且**即使 force 也绝不删未跟踪文件**(keep-set 不可信时,
删"不认识的"文件等于删用户的东西)、还原前必须留下一份能回到"还原前"的安全 checkpoint。

**前端消息合并。** 屏幕上那一串是"服务端历史 + 本地实时"合出来的,是整个聊天里最
容易出重影和顺序错乱的地方(bw 修过一次、cq 又碰过一次)。8 个用例:乐观气泡在服务端
回声到达后消失、**重复发同一句话不会被误吞**、实时行按时间戳插回它所属的那一轮、
同样输入给同样顺序、时间戳损坏不炸链。

**常驻池可观测面。** 4 个用例钉形状自洽(`size = busy + idle`、max 不能是 0 ——
界面会显示 0/0)与通知钩子的注销安全。

vitest 从 805 → **856**(+51)。

### G3 · 分包

`AppContent` 一个块 675 kB,里面最大的两坨与"应用逻辑"无关:

- **vendor-markdown**(450 kB):react-markdown + remark/rehype + katex + 三十多个
  micromark/mdast/unist 上游小包。按**包目录**匹配而不是逐个列 import ——
  逐个列必然漏,而漏掉的那个会被折回 AppContent。
- **vendor-icons**(63 kB):lucide-react。

两者几乎从不变,浏览器缓存能一直命中(AppContent 每次发版都变);而且它们被多个

(`payload` 为空时连模块都不拉)。

**AppContent 675 kB → 466 kB(−31%)**,首屏还少了一份不会用到的 markdown 管线。

## 2026-08-27 · cv — F10 大件三选(跨文件搜索 / 编辑器多标签 / 终端多标签)

### 跨文件全局搜索

文件树的搜索框只匹配**文件名**;人真正要找的常常是内容 —— "那个函数叫什么来着"、
"这个常量还有谁在用"。此前唯一的办法是打开终端自己 grep。

`GET /api/projects/:projectId/search?q=&glob=&caseSensitive=&regex=&wholeWord=`,
用 ripgrep 跑(已是依赖,尊重 .gitignore、跳过二进制、比任何 JS 实现快一到两个数量级)。

三道闸,都是为了让"一次搜索"不可能变成"一次拒绝服务":

- 搜索根**必须**是调用者可见的项目目录(`resolveVisibleProjectRoot`,拿不到就 404,
  与"项目不存在"同形);
- 结果数(300)、单行长度(400 字符)、单文件大小(2M)、超时(15 秒)都有硬上限,
  **截断如实上报** —— 少给结果而不说,比给少了更糟,用户会以为项目里就这么多;
- 模式与 glob 都走 `--` 之后,用户输入以 `-` 开头也不会被当成 rg 的参数。

界面上是一个独立面板(Ctrl/Cmd+Shift+F,与聊天里的 Ctrl+F 会话内查找错开一个 Shift)。
结果**按文件分组**(一屏 300 条平铺没法读,而"哪个文件里有"通常就是答案);
默认按**字面量**而不是正则(多数人搜的是字面量,而正则里的 `.` `(` `*` 会让结果
莫名其妙);点一条命中就在编辑器里打开那个文件。

返回的是**相对项目根**的路径 —— 绝对路径既没用,又泄漏服务器目录结构。

**顺带修掉一个潜伏的部署坑**:`@vscode/ripgrep` 导出的二进制路径指向它 postinstall
阶段下载的文件,而 postinstall 在两种常见情况下不跑 —— 安装机器没有外网(内网部署),
或者用了 `npm ci --ignore-scripts`(不少安全基线要求)。这时 spawn 抛 ENOENT,
用户看到的是一串看不懂也不知道该装什么的报错。现在自带的不在就回落到 PATH 里的 `rg`,
两者都没有时给一句能照着做的话。**会话搜索**用的是同一个解析器,一并修好。

### 编辑器多标签

之前一次只能开一个文件 —— 对着一份代码改另一份(照着接口写实现、比对两处配置)时,
每看一眼就要把当前文件关掉,回来还要重新找。

- 打开的文件按**打开顺序**排,关掉当前那个之后落到**左边**那个 —— 可预测,
  而不是跳到一个随机的;
- 少于两个文件时不画标签条(一个标签的标签条只是白占一行,而侧栏编辑器本来就窄);
- 中键点击关闭(与浏览器、VS Code 一致);
- 切标签时给 CodeEditor 换 key —— 不换的话 CodeMirror 会把上一份文档的撤销历史带过来;
- 未保存改动的确认只在**切走/关掉当前那个**时问:后台标签根本没挂载编辑器,不可能有改动;
- 上限 12 个:再多标签条自己就不可读了,而"开了三十个文件"通常意味着人想要的其实是
  搜索(这轮的另一半),不是标签。

### 终端多标签

一个终端跑着构建、另一个想看日志 —— 之前只能等,或者去别处开一个 shell。

服务端的 PTY 池本来就按键分,天然支持多个;缺的只是**每个标签一个 id**。PTY 键此前是
`u<用户>_<项目路径>_<会话|default>`,于是同一个项目下开第二个终端会**连到第一个的
PTY 上** —— 两个标签共享一个 shell,输出互相串,关一个另一个跟着哑。现在键里带上
`terminalId`(只取字母数字和连字符,这个值直接进键);不带 id 的老客户端落到空后缀,
行为与改动前逐字一致。

非活动标签**用 CSS 藏起来而不是拆掉**:卸载会断开 websocket,回来时只能靠回放缓冲
捞一小段,正在跑的命令就看不到了。上限 6 个。

带命令的一次性终端(登录、setup-token)不给标签条 —— 那些是任务终端,加标签既没
意义又会把布局挤乱。

**踩到并修掉的一个坑**:标签的增删原本写在 `setTabs` 的 updater 里顺带改 id 计数器和
活动标签。updater 必须是纯函数 —— React 在 StrictMode 下会跑两遍来暴露副作用,
那样 id 会跳号、活动标签会被设两次。改成先算好再一次性提交。

## 2026-08-27 · cu — F9 文件树补课 + F11 设置跟着账号走

### F9 · 文件树三件

**拖放到指定文件夹**。`handleItemDragOver` / `handleItemDrop` 在
`useFileTreeUpload` 里写好了,但**从来没接到任何节点上** —— 于是拖进来的文件永远
落在项目根,拖到哪个文件夹上都一样。现在接线了:悬停的目录高亮,松手就落在那儿。
只有**目录**接受定位 —— 拖到文件上没有意义,反而会让人以为能"放进文件里"
(探针两条都钉住:目录行 `preventDefault` 且高亮,文件行不响应)。

**多选批量**。选择模式用一个显式开关进入,而不是"点着点着就进去了" —— 文件树的
默认动作是打开文件,把它偷偷改成选中会让人删错东西。开关之外,按住 Ctrl/Cmd/Shift
点击也算选中(与文件管理器一致)。选中后可批量下载、批量删除;删除**确认一次**
然后逐项删(批量已经确认过了,逐项再弹一次就成了点二十下"确定"),确认里写清有
几项 ——「确定删除?」配上一个看不见数量的选择集合,是最容易造成事故的组合。

**Cmd+N / Cmd+Shift+N 做实**。这两个组合原来只写在按钮的 tooltip 里,按下去什么
都不会发生 —— 是个纯粹的谎言。现在真的接上,并且只在文件页挂载、且焦点不在输入框
时生效(否则会把编辑器里的 Cmd+N 抢走)。

- 冲突用时间戳:两边都带 `updatedAt`,新的赢。没有它的话,"在 A 改完打开 B"和

### F8 · 回收站批量操作、清空、保留期

归档是**软删除**:行还在,随时能恢复。好处是误删可挽回,代价是**它永远不会自己

  6 小时一轮,每轮 200 条封顶(首次开启时回收站里可能几千条,不该一口气占住事件循环)。

批量接口 `POST /api/providers/sessions/bulk`(archive / restore / delete):

- **逐条**过可见性判定。看不见的既不动也不报错 —— 报错等于告诉调用方那个 id 存在,

- 单次 1–500 条,超出 400。

> 范围说明:批量操作做在**回收站**里,因为痛点在那儿(几百条要一条条删)。活跃列表

## 2026-08-27 · cs — F7 回合内排队 + F14 体验细节三件

### F7 · `chat.send` 撞上在跑的回合不再直接打回

之前撞上就 `RUN_IN_PROGRESS`,那条消息**就没了**。前端确实有自己的排队(cb 轮那条,
存在浏览器 localStorage 里),但它盖不住两种情况:

1. **判定竞态** —— 前端以为空闲、服务端还在跑(上一轮结束的帧还在路上,或者
   另一台设备刚发过一条)。这时前端不入队,而是照常发,然后吃一个协议错误。
2. **关掉标签页** —— localStorage 里的队列没人替它发。

现在服务端**收下一条**,回合结束自动续发:

- 只收一条。排两条以上等于允许把一串指令扔进黑盒,而中间那条的结果用户根本没看到
  就发了下一条 —— 那不是排队,是盲发。第二条明确回 `QUEUE_FULL`,并告诉他已经有
  一条在等,**不会**悄悄顶替。
- **中止把排队那条一起带走**:"停"就是停,不是"停这条跑下一条";而且要说清楚是被
  中止带走的,否则消息看起来凭空消失。
- 30 分钟不发就作废(半小时前那句话的语境早就不在了),同样有提示。
- 排队状态**广播给所有能看到这条会话的人**,并随 `chat.subscribe` 的 ack 返回 ——
  刷新页面、换设备后"有一条在等"这件事不能只活在发起它的那个标签页里。
- 新增 `chat.cancel-queued` 撤销;界面上复用排队卡片,措辞区分开(「服务端已收下 ·
  本轮结束后自动发送 · 关掉页面也有效」),且没有铅笔 —— 那条已经在服务端了,
  没有"编辑"可言。
- 兜底:回合也可能不是从 `chat.send` 的 finally 里结束的(看门狗、运行时崩溃),
  那条路上没人来接排队消息。`chat.subscribe` 顺手检查一次,页面回到这条会话时补上。

测试断言的是**副作用**(第二条最终有没有真的进运行时、是不是在第一条之后进的),
不是回了什么帧 —— 只看帧的话,一个"回帧但从不续发"的实现照样能过。

### F14a · 打开对话即预热运行时

打开一段旧对话到发出第一条消息之间,总有几秒到十几秒的空档:用户在读上文、在打字。
冷启动那几秒本可以塞进这个空档,而不是让他按下回车之后再等。

`chat.subscribe` 现在会拉起该会话的常驻运行时。三道闸避免它变成资源黑洞:

- **只有单条订阅才预热** —— 批量订阅是侧栏在同步"哪些会话在跑",一次十几条;
  给它们逐个预热会把 20 个名额瞬间填满 speculative 进程,再配上按人公平淘汰,
  结果是互相踢来踢去;
- 只对**已有原生会话 id** 的对话预热(新会话本来就要新建进程,提前建一个没有
  resume 目标的空进程只是白占名额);
- 同一会话 60 秒内只预热一次。

全程 best-effort,失败一律吞掉 —— 预热是优化不是功能,失败最多回到原来的速度。

### F14b · 常驻进程被挤掉时推一条状态帧

被名额挤掉本身是正常且必要的,问题在于它**静默**:那段对话的下一条消息要重建进程
并 resume,慢几秒,而用户只会觉得"今天特别卡"。现在推一条 `status` 帧
(不是 error —— 什么都没坏,也没有任何东西需要用户处理),界面能给一句可解释的提示。

claude-sdk 不认识 websocket 层,通知器由组合根注入。

### F14c · 重启打断的回合补「请重发」标记

一个回合的中断在库里长这样:显示日志的**最后一条是用户消息**,后面什么都没有。
之前这种会话打开后是静默的 —— 用户看到自己那句话孤零零挂在最后,不知道发生过什么,
也不知道该重发。

启动时扫一遍,给每条这样的会话补一条说明。判定安全的前提是**启动那一刻没有任何
回合在跑**(正在流式输出的会话看起来一模一样),所以这件事只能在启动那一刻做,
晚一秒都可能误伤。用窗口函数一次取回每个会话的最后一行,而不是先列会话再逐个查。

幂等:补的那条本身是 durable 消息,补完最后一条就不再是用户消息,下次启动自然跳过
(实测连起两次,第二次补 0 条)。

## 2026-08-27 · cr — F6 管理面(root 只读统计 + 每账号附件配额 + runtime 公平淘汰)

服务器状态面板原来只答「这台机器怎么样」(负载/内存/磁盘)。真正会把 Prism 拖垮的
却是**进程内的池子**,而它们之前一个都看不见 —— 名额满了只表现为"某人发消息很慢",
内存涨了只能猜是谁。这轮把它们摊开,并把两处"全局一个数"改成按账号。

### 进程内资源快照(`GET /api/admin/stats`,root)

- **常驻会话池**:占用/上限、在跑几个、一次性溢出槽用了几个、空闲回收阈值;
- **在飞回合**:数量 + 最早那条的开始时间;
- **PTY**:总数、已连/断开待回收、接管态、回放缓冲字节;
- **历史缓存**:条目数与字节数(进程里最大的一块可变内存,默认 32MB 预算);
- **待审批账号数**。

常驻会话与 PTY 都**按账号切一份**并带上用户名 —— "满了"本身不可行动,"被谁占满了"
才可行动。

面板**只读**,没有回收按钮:一个能一键杀掉别人正在跑的回合的开关,风险远大于它省下
的事;真要收,重启服务是更诚实的动作。

数据由组合根注入(admin 模块不直接 import `claude-sdk.js`),与 shell 模块注入
`releaseConversation` 同一套约定。

### 附件配额:每账号可覆盖

配额本来就是按账号算的,可之前只有一个全局值(`PRISM_ATTACHMENT_QUOTA_MB`)。
多数人用不到 1 GB,个别人要传一堆设计稿 —— 为那一个人抬高全局值,等于给所有人
都开了那么大的口子。

- `users.attachment_quota_mb`(新列,NULL = 跟随全局)——**存量账号零影响**,
  这是测试第一条钉的东西;
- `GET /api/admin/attachment-usage`:每个账号的用量/上限/覆盖值,按占用降序
  (root 打开这页时想知道的永远是"谁占得最多");
- `PUT /api/admin/users/:id/attachment-quota`:设置或清除,留空即回默认,写审计日志;
- **0 和负数一律当成"清除覆盖"**,不是"覆盖成 0" —— 把某人配额设成 0 意味着他一个
  字节都传不了,那应该是另一个开关,不该是输入框手滑的后果;
- 用户自己的「我占了多少」那一页也跟着按账号取,否则他看到的数和实际拦他的那个数
  不是一回事。

### 常驻池按人公平淘汰

名额满时原来是全局 LRU —— 合理但不公平:一个人开二十个会话就能把池子占满,之后
每个新会话都去挤**别人**那条最久没用的。别人每轮重建 runtime(等于每轮多一次冷启动),
占了十九个的那位一点代价都没有。

现在先看谁**总共**占得最多(在跑的也算,它们同样占着名额),从这个人的空闲 runtime
里挑最久没用的下手;打平了再比 LRU。代价落在造成拥挤的人身上。排序抽成纯函数
`orderRuntimesForEviction`,五个用例钉住(含"在跑的不进候选但算占用" —— 否则
跑满的人反而免疫)。

### E7 · 项目列表 N+1 批量化

侧栏第一屏那次 `/api/projects` 是**每个项目三次查询**:首页会话、会话计数、
授权名单。30 个项目就是 90 次 prepare+执行,而且全压在首屏。

改成循环前批量取三份、循环里只做内存查表:

- 会话首页用窗口函数一次取回所有项目的前 N 条
  (`ROW_NUMBER() OVER (PARTITION BY project_path ORDER BY …)`,排序与单项目
  分页那条**逐字一致**);只服务 `offset=0`(列表的默认形态),翻页仍走原来的
  单项目路径,不为少见路径把 SQL 复杂化。
- 会话计数一次 `GROUP BY`。
- 授权名单一次 `IN`。

**3N 次查询 → 3 次固定查询**。探针实测两条路径给出同一份结果:批量路径与
翻页回落路径的条目、总数、`hasMore` 全对得上。

### E9 · checkpoint 不再每回合全量拷贝 untracked

每个回合前都会给工作区打一份 checkpoint,而 untracked 快照原来是**每轮全量
`copyFile`**。仓库里躺着构建产物或数据文件时,这是每轮几百 MB 的纯拷贝。

现在带一份"上一份 checkpoint 存过什么"的索引,同一路径只要
**size + mtimeMs + inode 三者全同**就硬链到上一份副本:没有读写、不占额外磁盘、
内容与拷贝逐字节相同。判据比 git 自己的 stat 缓存还严一档(git 只看 size+mtime)。
链接失败(跨设备 / 文件系统不支持 / 上一份已被清理)一律静默回落成拷贝。

要点:
- 硬链接共享 inode,老 checkpoint 被 TTL 清掉时只掉一个链接数,**新的那份照样
  能读、能还原**;
- 还原走的是 `copyFile`(store → 工作区),store 的 inode 不会被带进工作区,
  改工作区文件不会改到快照;
- 复用的字节**不计入** 200MB 快照预算 —— 预算管的是这份 checkpoint 真正占的
  磁盘,而硬链接一个字节不占,且内容确实完整存下了(不该因此判 `incomplete`)。
- 找上一份不走全量 `listCheckpoints()`(那要 parse 整个 store 的 meta):按
  checkpoint id 里的时间戳倒序扫,命中同一个 cwd 就停,正常情况下第一条就是。

实测:同一个 3MB untracked 文件连打三份 checkpoint,store 占用从 9.4MB 降到
3.1MB;改过的文件照常重新拷贝,旧 checkpoint 里仍是旧内容。

### E10 · 归档会话列表分页 + 可见性下推 SQL

原来是**全表捞回所有归档会话,再逐行跑一次 `canViewerSeeSession`** —— 而那一次
判定自己又要三次查询(会话行 / 项目行 / 授权名单)。归档攒到几百条,打开一次
归档面板就是上千次查询;而且过滤发生在 JS 侧,**根本没法分页**(先分页再过滤,
每页剩几条全看运气)。

- 可见性下推进 SQL:`sessions LEFT JOIN projects` 再套同一段判定。会话没有自己的
  owner,它挂在项目上;项目行**可能不存在**(watcher 先索引了 transcript),
  这时回落到"会话自己记的路径在不在公共目录下" —— 与 JS 侧同义。
- 那段判定现在只有**一份**:新增 `modules/database/visibility-sql.ts`,项目列表

全库深读方案的第二轮:运行时/终端/关停链路的健壮性。

### B1 · 常驻 runtime 去掉 maxTurns=100 累计上限

streaming-input 模式下一个 query 贯穿整段对话,`num_turns` 是**跨用户回合累计**
的 —— 设 100 意味着聊到第一百个来回(或几轮重 agentic 任务)后必撞
`error_max_turns`,越活跃的会话死得越早,而一次性路径从没设过。删掉;单回合失控
自有 turn 看门狗(空转/工具静默超时)兜着。

### B2 · 外部 API 同步路径纳入 run registry(消除双写)

`POST /api/agent`(stream / 非 stream)此前不 `startRun`、不查 holder —— 同一
provider 会话可被网页聊天的常驻 runtime 与这条同步回合**同时写同一份 transcript**。
现在:指向已有会话(appSessionId 有值)时占运行位,冲突回 **409**;并把 runId 传给
queryClaudeSDK,顺带让 `chat.abort` 能中止同步回合;finally 里释放运行位。全新会话
(无 appSessionId)无可冲突目标,语义不动。

### B3 · 一次性路径纳入并发预算

有意的一次性回合(外部 API 的 `oneShot`、或 `PRISM_PERSISTENT_SESSIONS=0`)此前
直呼 `queryClaudeSDKOnce`,绕开 `MAX_RUNTIMES + overflow` 全局预算,只剩 IP 限流
兜底 —— API 流量可无上限打出上百个 CLI 子进程。改为同样走 `runOneShotFallback`
的预算闸(不发"已降级"提示,只计数与配额)。

### B4 · abort 的 interrupt() 加超时,子进程僵死也能停

用户按"停止"最常发生在子进程僵死时,而 `interrupt()`(与子进程的协商)此时永不
返回,`await` 挂死、终止帧发不出,停止按钮要等看门狗兜底。新增 `interruptWithTimeout`
(默认 5s 竞速,迟到的 reject 内部吞掉防 unhandled);两条 abort 路径超时即升级到
**硬撕**(abortController)。为此给一次性路径也补了 abortController(此前只有持久
路径有),并让 `addSession` 记录它。

### B5 · PTY 回放缓冲改字节预算

终端断线重连的回放缓冲此前只数条数(5000 chunk),单块不设限 —— `cat` 大文件时
单个 PTY 能挂住几十 MB 到 30 分钟超时才回收(chat 侧早改字节预算,shell 漏了)。
改为**字节为主(2MiB)+ 条数兜底**双预算,裁剪逻辑抽成纯函数 `shell-replay-buffer.ts`。

### B6 · WebSocket 设 maxPayload=4MiB

ws 库默认单帧上限 100MiB —— 任一已登录 socket 一帧就能造成 `JSON.parse` 内存/CPU
尖峰。聊天入站帧(文本+图片引用+审批应答)远小于 4MiB,大文件走 HTTP 分片通道。
超限帧由 ws 以 1009 关闭。

### B7 · 关停清理:空闲常驻池 + 备份首跑定时器

## 2026-08-25 · bs — 会话排序:只点一下不该顶到最前,按真实会话时间排

- 预热 / resume 碰 mtime 但没说话 → 最后消息时间不变 → **排序不动**;

## 2026-08-25 · bn — 上传分片竞态 + 跨会话流式串味

体检里两条「两个东西同时来就出错」的并发 bug。

### 一、分片同-index 并发到达 → 整单作废

`/land/chunk` 的 `session.nextIndex = index + 1` 在 `await appendChunkFile` **之后**
才推进。触发场景很现实:反代(nginx 之类,分片上传本来就是为穿它而生)在源站
还在慢盘 append 时先回 504 → 前端重发**同一片** → 第一个 handler 还没推进
`nextIndex`,重发的第二个再次通过顺序门 → **两个都 append 到同一个 `.part`**
(字节还会交错),`received` 翻倍 → complete 命中 `received !== declaredSize` →
最大 500MB 的整单被判「不完整」作废。重试机制反而帮了倒忙。

**为什么不能只把 `nextIndex` 挪到 await 前**:那样两个**不同** index 的请求会
同时通过顺序门、同时 append 到同一文件,一样交错。所以「判序 + 追加 + 推进」
必须在一把**每会话串行锁**里一气呵成(`withSessionLock`):同 index 重发等到锁时
`nextIndex` 已推进 → 命中幂等分支被丢弃;下一个 index 排在前一个之后再 append,
顺序不乱。

实测:同 index=0 并发两发,两个都回 `received:1000000`(没翻倍),补完 1、2 后
complete 成功,落地文件正好 3000000 字节。

### 二、流式缓冲全局共享 → 当前会话气泡显示别的对话

整个 realtime hook 只有**一个** `accumulatedStreamRef`(字符串)和**一个**
`streamTimerRef`。两条 run 同时向本浏览器推流时(队列自动发到后台会话、多会话
同时 processing 都会),两路 token 交错进同一个缓冲,100ms 定时器到点把「A+B
混合文本」刷给其中一个 sid 的气泡。当前所看会话会短暂显示另一段对话的字
(`complete` 后 `refreshFromServer` 自愈,但看着像串台)。

**改法**:缓冲与定时器都**按 sessionId 分桶**(`Map<string,…>`)。每个会话的
定时器闭包捕获自己的 sid 与 provider,刷的永远是它自己那段缓冲。`stream_end` /
`complete` 只清自己这一桶。

### 验证

- 分片竞态:并发同-index 两发不翻倍,complete 成功,落地字节精确(见上)
- 流式:会话正常渲染、无 pageerror / console error(改的是缓冲键控,渲染路径未动)
- 门槛:typecheck 双端;eslint `src/ server/` **0 错误**(44 warning 不变);
  vitest **638** 全过;双端构建通过。无新增依赖、无建表,`package-lock.json` 不变。

## 2026-08-21 · bj — 回看历史消息「叫你滚,又滚不动」

用户报的是"加载慢":回看历史时页面写着「向上滚动以加载更多」,可是**滚不动**。

不是慢,是**死锁**。

### 它是怎么卡死的

加载下一页**只由滚动事件驱动**。而首屏那一页 20 条消息,经过工具行折叠之后
可能只渲染出**两三个 DOM 行** —— 一整轮 38 次工具调用会被收成一句
「执行 13 条命令 · 读取 13 个文件 · 搜索 12 次」。

于是:

```
撑不满容器  →  没有溢出  →  没有滚动条  →  永远不触发 scroll  →  再也不取下一页
```

提示还立在那儿写着「向上滚动以加载更多」—— 一句用户**物理上做不到**的指令。

复现(360 条消息、每轮 38 次工具调用的会话,900px 视口):

```
显示 10 / 360 条消息 向上滚动以加载更多
scrollHeight 695 / clientHeight 695   canScroll = false
```

剩下的 350 条,等多久都不会来。

### 改法

**先把视口填满,再把方向盘交回给用户。** 内容变化后量一次:还能往上取、
但容器已经滚不动了,就自动再取一页,直到真的出现溢出或者取完为止。

三个坑都是在实测里一个个撞出来的,记在这儿免得下次再踩:

1. **不能靠 effect 重入驱动循环。** `sessionStore.fetchMore` 在 `return`
   之前就 `notify()`,React 立刻重渲染、effect 重入 —— 而那一刻上一轮的
   `isLoadingMoreRef` 还锁着,这一次调用直接空转返回。补一轮就停死
   (实测 11 → 22 条之后 40 秒不动)。所以循环由 effect 自己拿着。

2. **不能让 cleanup 里的 `cancelled` 收尾。** 取完一页后 `loadOlderMessages`
   的身份变了,effect 先跑 cleanup 把循环判死、再重跑;重跑那一刻旧循环还停在
   `await` 里没走到 `finally`,`autoFillBusyRef` 仍是 true,新一轮直接返回。
   两边互相让路,还是补一轮就停死(实测 92 → 113 条)。
   **退出条件只认会话** —— 只要还停在同一个会话上,这个循环就一直是它的主人。

3. **「取不到」不等于「没得取」。** `isLoadingMoreRef` 是和用户滚动共用的一把锁,
   补页途中恢复滚动位置会带出 scroll 事件,`handleScroll` 同样会去抢。撞上锁时
   `loadOlderMessages` 只返回 false —— 把它当成"取完了"就是提前收工
   (实测第 8 轮撞锁,停在 92 / 360)。撞锁要**等一等再来**。

还有一个更阴的:**「能滚了」得站得住脚才算数**。补页过程中容器会短暂地高出来
一点点(加载提示、滚动位置恢复、markdown 二次排版都会),量到那一帧就收手,
等它缩回去又滚不动了 —— 实测量到 `706 / 695` 判定收工,落定后是 `712 / 712`,
页面照样是死的。所以量到溢出**先等一下再量一次**,两次都站得住才真收手。
收工之后内容再缩回去(工具行折叠、窗口变大),还会把循环重新叫起来。

轮次上限 30 是"取不满就停手",不是"取够就行":万一整段都是被折叠的工具调用,
30 轮之内还撑不满就停下把决定权交给用户 —— 他还有「加载全部」那条路。
上限不随重新唤起而重置,所以不会没完没了。

### 验证

同一份语料、同一个视口的 A/B(360 条消息,每轮 38 次工具调用):

| | 加载条数 | scrollHeight / clientHeight | 能滚吗 |
|---|---|---|---|
| 改之前 | **10 / 360** | 695 / 695 | **否 —— 永久卡死** |
| 改之后 | 123 / 360 | 848 / 695 | 是 |

改之后再用滚轮往上滚,`scrollHeight` 从 848 涨到 1870,提示消失 —— 360 条全部到齐。

按视口高度自适应,不多取:

| 视口 | 自动补到 | scrollHeight / clientHeight |
|---|---|---|
| 700px | 82 条 | 642 / 495 |
| 900px | 123 条 | 848 / 695 |
| 1080px | 164 条 | 1054 / 875 |

**正常会话完全不受影响**:另造一个 360 条纯文本对话,首屏 20 条就已经
`2309 / 695` 撑满了,自动补页**一轮都没跑**,显示条数原地不动还是 20,
往上滚照常翻页(20 → 80)。

## 2026-08-20 · ba — 外部 API:先领会话号,再干活

需求是"调 Prism 的接口起一段会话,拿到 id 直接拼前端链接点进去看"。
现在的 `/api/agent` 做不到两件事:**id 只有回合跑完才回**,而且**没法指定 id**。

### 领号与干活拆开

新增 `POST /api/agent/sessions`(同 API key 守卫),不跑任何回合,毫秒级返回:

```
POST /api/agent/sessions  { projectPath }
→ 201 { sessionId, sessionPath: "/session/<id>", projectPath }
```

关键是它**真的在库里占一行**(`createAppSession`),不是发一个 UUID 就完事 ——
占了行,那个链接当场就能打开(先是一段空对话),而不是"会话不存在"。

第二步照常 `POST /api/agent`,把领到的 id 放在 `sessionId` 里。

### `sessionId` 的三种含义,判据只有一条

传进来的 id 是"续对话"还是"用这个 id 新建"?判据是**库里那行的
`provider_session_id` 空不空**:

| 库里 | 含义 |
|---|---|
| 没这行 | 老语义:当成 provider 原生 id 续对话(**行为不变**) |
| 有行、`provider_session_id` 空 | 领过号还没跑过 → **用这个 id 新建** |
| 有行、`provider_session_id` 有值 | 续那个 provider 会话 |

第二种若按 resume 处理,CLI 会去找一份根本不存在的 transcript,直接失败。

新建靠 SDK 的 `Options.sessionId`(实测:transcript 原样落成 `<id>.jsonl`)。
于是**应用侧 id、provider 原生 id、transcript 文件名三者同值** ——
链接、侧栏、磁盘对得上。watcher 之后扫到走的是
`INSERT … ON CONFLICT(session_id) DO UPDATE`,原地补 `provider_session_id`,
不产生重复行;同步路径跑完还会主动回填一次,不等扫描周期。

那个"只改一行"的写法有个坑:`mapCliOptionsToSDK` 没解构 `newSessionId`,
而 server 是 ESM(严格模式),直接引用未声明标识符**每个回合都抛
ReferenceError**,不是"传了才出问题"。

### 可选的 `async: true`:发起即走

想连第二步的等待都省掉,可以传 `async: true` —— 回合**开跑之前**就 202 返回
`{ sessionId, sessionPath }`,这一轮转到后台,输出走**聊天网关**广播。
所以人点开链接是**实时看着它跑**,不是等跑完再刷新;断线重连有补发游标,
`chat.abort` 也能用,显示日志(az 轮)照记。

为此 `ChatSessionWriter` 要允许"一个浏览器都没连着"的 run:构造函数原来
无条件把 `options.connection` 塞进集合,传 null 等于给每一条出站消息埋一颗
`null.readyState`。现在有值才加。

`async` 与 `createBranch` / `createPR` 互斥(响应先发,结果没地方回报),
`cleanup` 在它下面不生效(会话是留着给人看的,不能删掉它的项目目录)。

### 顺手修掉:非流式响应一直是空的

`ResponseCollector` 只认 `type: 'claude-response'` 的**字符串**帧 —— 老 CLI 的
线格式。走 SDK 之后推过来的一律是规范化**对象**,两个条件一个都不成立,
于是非流式 `/api/agent` 的 `messages` **恒为 `[]`**、`tokens` 全 0,静默很久了。
按 kind 认之后实测能拿到回答与真实用量(`{"content":"收到"}` / 81349 tokens)。

### 病根:`role: 'user'` 被当成了「用户说的」

Claude 协议里 `role: 'user'` 只是**帧的方向**,不是**发言的人**。同样走 user 帧的还有:

`nonHumanUserTurnReason(raw)`:`isMeta` / `isSidechain` / `isSynthetic` /
