## 2026-08-20 · ay — ax 只修了一半:提交路径上还有同一个窄判断

ax 之后 `/compact` 仍然报「既不是内置命令,也没有对应的命令文件」。
原因是**同一个错误判据在两个地方**,ax 只改了菜单那处。

`handleSubmit` 里对以 `/` 开头的输入做截胡,判据是:

```ts
if (matchedCommand && matchedCommand.type !== 'skill') {
  executeCommand(...)   // → /api/commands/execute
```

`type !== 'skill'` —— 和菜单里犯的是同一个错:除技能外全送去 execute 端点。

**而 ax 反而让这条路更容易走到**:菜单现在会把 `/compact` 稳稳放进输入框,
用户再按一次回车发送,正好落进这个截胡分支。改成两处共用 `isPromptCommand`。

### 还有一层:客户端会无差别盖掉 type

`useSlashCommands` 拿到 `/api/commands/list` 的 `builtIn` 数组后,
给**每一项**盖上 `type: 'built-in'`。而那个数组里混着 `cliPassthroughCommands`
(`/compact` `/clear` `/init` `/review` `/todos` `/rewind` …)——
服务端给它们标的是 `namespace: 'cli'`。

所以判据**不能只看 `type`**,必须同时认 `namespace: 'cli'`(现有实现正是如此)。
新增两条回归用例把这层覆盖钉死。

### 验证

- 用例 5 → **7** 条(全库 **571**)
- 浏览器实测:输入框发送 `/compact` → 打到 `/api/commands/execute` **0 次**、无报错、
  输入框清空(说明作为普通提示词发给了 CLI);
  发送 `/help` → 打到 execute **1 次**、无报错(内置命令行为不变)。

## 2026-08-20 · ax — 斜杠命令两个真 bug:Tab 不是补全;CLI 命令被送错地方

两处报障其实是**同一段分发代码**的两个面。

### 1. 「除了 skill 都不支持 Tab 补全」

`selectCommandFromKeyboard` 里 **Tab 和 Enter 走的是同一个分支**:技能 → 打进输入框,
其余 → **立刻执行**。所以按 Tab 的时候,只有技能看起来"像补全",其余的一按就跑了。

改成按键分流:

- **Tab = `complete`** —— 任何类型都**只把命令补进输入框**;
- **Enter = `submit`** —— 才按类型决定进输入框还是交服务端执行。

实测:输入 `/hel` 按 Tab → 输入框变成 `/help `,不执行、不报错。

### 2. 「Error executing command: Command path is required for custom commands」

命令列表有两个来源:`/api/commands/list`(内置 6 条 + `.claude/commands/` 里的自定义)
和 `/api/claude/slash-commands`(**CLI 自带的** `/compact`、`/clear`、`/init`…)。

而 `/api/commands/execute` 只认两种:**有 handler 的内置命令**,和**带 path 的自定义命令**。
CLI 自带的那批两样都没有 —— 于是每点一次就撞在
「Command path is required for custom commands」上。

原来的判断只挑出了技能(`isSkillCommand`),换成 `isPromptCommand`:
**技能、CLI 命令、以及任何缺 path 的非内置命令,一律打进输入框当提示词发给 CLI 去解释。**

实测:输入 `/comp` 按 Enter → 输入框变成 `/compact `,不再报错。

### 顺带

- 服务端 handler 查表**对前导斜杠不敏感**(键是 `/help`,传 `help` 也认);
- 那条报错补上了命令名和一句人话,说清楚"CLI 自带命令请直接在输入框里发送";
- 新增 5 条用例(`slashCommandRouting.test.ts`)钉住六个内置命令仍走服务端、
  技能与 CLI 命令走输入框、自定义命令缺 path 时不再撞报错。全库 **569** 条。

## 2026-08-20 · au — 技能正文注入:结论是没漏,但补上结构级判据;logo 继续放大

有反馈说「技能全文(`# Keybindings Skill` 那种)仍会泄漏成用户气泡」。
**先做了受控实验才动手**:在本机真调一次 `Skill { skill: 'pdf' }`,再回头读 transcript。

真实注入行长这样(字段一字不改):

```
type=user  isMeta=true  sourceToolUseID=<Skill 那次 tool_use 的 id>  turnCompanion=true
content[0].text = "Base directory for this skill: /root/.claude/skills/synced/pdf\n\n# PDF Processing Guide…"
```

**三重可判**:`isMeta` 已经在第一道门槛拦下,`Base directory for this skill:` 前缀
也在清单里。也就是说反馈里那条"漏网"复现不出来 —— 那个测试喂的是**手搓的、
不带任何标记、直接以 `# Keybindings Skill` 开头**的行,而 CLI 并不产生这种行。

反馈提的两个方案也都不采用:识别 `Launching skill: X` 再丢掉紧随其后的那条,
是**位置启发式**(实测那条 tool_result 内容就是 `Launching skill: pdf`,而它后面
那条本来就已经被拦掉了);往前缀清单里塞更多技能特征,则是拿内容猜结构。

但反馈指出的隐忧是对的:这一类的防线不该只靠 `isMeta` + 一条文本前缀。所以补两条
**结构级**判据,把它从"内容级"升级成"结构级":

- **`sourceToolUseID`** —— 这条 user 行是某次工具调用**造出来的**,天然不是键盘输入。
  注意别和 `sourceToolAssistantUUID` 搞混:普通 tool_result 行带的是**后者**
  (本会话 362 行全是),判错就等于把所有工具结果一起吃掉。已单独立用例守着。
- **`turnCompanion`** —— 附在某个回合上的伴随行(图片尺寸说明、技能正文……),
  本身不是一个回合。

优先级也写进注释了:**结构判据在前,内容前缀只当兜底** —— 实时 SDK 流上没有这些
transcript 字段,那时前缀才是唯一防线,所以两者都要留着。

## 2026-08-20 · as — 根治「凭空冒出来的用户消息」

### 病根:`role: 'user'` 被当成了「用户说的」

Claude 协议里 `role: 'user'` 只是**帧的方向**,不是**发言的人**。同样走 user 帧的还有:

- 工具结果(`tool_result` 块)—— 正常,单独成 `tool_result` 消息;
- **子代理(Task/Agent)的整段对话** —— 带 `parent_tool_use_id`(实时流)
  或 `isSidechain: true`(写进 transcript 时);
- CLI/SDK 的机器耳语 —— 空响应重试、坏工具调用重试、压缩续接、
  `<system-reminder>`、Skill 说明书注入、本地命令占位……

而 `normalizeMessage`(实时流与历史回放**共用的唯一出口**)判定"这是不是用户气泡"
只看两件事:`raw.isMeta !== true`,以及内容是否命中一份 `startsWith` 前缀黑名单。
`parent_tool_use_id` 在上游 `transformMessage` 里**已经算好挂在同一个对象上了**,
从头到尾没人读过。于是子代理被派活时的那句 prompt(界面上见到的
「Reply with exactly the text AGENT_OK…」)一路畅通,渲染成了用户气泡。

三条漏进来的路,现在逐条堵掉:

### 1. 新增 `transcript-provenance.ts` —— 出处判定收在一处

`nonHumanUserTurnReason(raw)`:`isMeta` / `isSidechain` / `isSynthetic` /
`isVisibleInTranscriptOnly` / `parent_tool_use_id` / `subagent_type` /
`userType === 'agent'` / `origin.kind !== 'human'`,命中任一即判为非人类回合。

**判定原则是反证,不是求证。** 只在拿到"这不是人发的"确凿证据时才拦 ——
反过来做(只放行 `origin.kind === 'human'`)会把老版本 CLI 写的历史整段吃掉,
`origin` 是后加的字段,老 transcript 里真正的用户消息同样没有它。

这个判定**只压住"把 text 渲染成用户气泡"**;同一条记录里的 `tool_result` 照常抽出来,
否则子代理的工具调用会从时间轴上整片消失(有用例守着)。

### 2. 历史回放丢掉 sidechain 行

`getSessionMessages` 原本只按 `entry.sessionId` 收行,子代理的对话跟主线程共用
sessionId,于是被整段铺进聊天。子代理的工具调用另有正路
(`subagents/agent-*.jsonl` → `parseAgentTools` → `subagentTools`),丢掉不缺信息。

### 3. `forwardSubagentText` 显式钉成 `false`

SDK 这个开关的默认值随 CLI 版本变过;为 true 时子代理的 prompt 与回复会直接以
user/assistant 帧发进主流。两条查询路径(一次性 + 常驻运行时)都显式写死。

### 顺带修的两处

- **注入过滤从"只看开头"升级为"整块摘除"**:`<system-reminder>` / `<local-command-caveat>`
  经常被**追加在用户原话后面**,`startsWith` 完全打不着,于是提醒原文混在用户气泡里
  一起显示。现在先摘块再判断:摘完还有正文就只显示正文,摘完空了才判为纯注入。
- **黑名单去重**:`session-conversations-search.service.ts` 手抄了一份(还多一条
  `Invalid API key`,两边已经漂了)。改成从新模块导入,单一事实源。

### 验证

- 新增 26 条用例(`user-turn-provenance.test.ts`),覆盖八种非人类标记 + 三种
  真用户回合的回归保护(含"老 transcript 无 origin 字段"这条最危险的路径);
- 拿真实 transcript 端到端跑历史接口:629 条归一化消息里**恰好 4 个用户气泡**,
  就是那 4 条真人发言,一条不多一条不少。
- 复刻截图里的五种假用户消息(子代理 prompt / sidechain / Skill 注入 /
  isSynthetic / 非人类 origin)全部拦下,三种真用户消息全部照常显示。
